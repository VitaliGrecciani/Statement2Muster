## 2. Адресные блокеры и условия закрытия

### R58-1 — P1: MCP обходит ранний бюджет тела запроса

`backend/app/core/middleware.py` применяет раннюю проверку размера и подсчёт входящего потока к `/api/v1/convert` и GPT-путям. Новые `/api/v1/mcp` и `/mcp` не входят в этот набор. FastAPI сначала загружает JSON как произвольный `Dict`, и только затем MCP создаёт `GptConvertRequest`. Поздняя проверка числа строк не защищает от уже принятого неограниченного JSON.

В контролируемой локальной пробе бюджет временно снижен до 256 байт: запрос с заявленным Content-Length 257 отклоняется GPT-маршрутом с 413, но оба MCP-пути возвращают 200. Для потока без Content-Length свыше этого бюджета результат тот же. Снижение бюджета — способ безопасно проверить ветвь middleware, а не измерение предельной нагрузки production.

**Условие закрытия:** одинаковая ранняя защита для обоих MCP-алиасов до JSON-десериализации, включая поток без Content-Length. Зафиксировать согласованный лимит MCP JSON и отдельные лимиты вложенных данных. Пробы с объявленным и фактическим превышением должны давать 413 без вызова конвертера. Не полагаться исключительно на недоказанную конфигурацию Nginx.

### R58-2 — P1: исходные значения попадают в неограниченную ошибку и логи

В `plugin_and_mcp.py:302` ручное создание `GptConvertRequest(**arguments)` выбрасывает Pydantic `ValidationError`. Это не FastAPI `RequestValidationError`, поэтому принятый ограничитель ошибок из `main.py` не применяется. Общий `except Exception` на строке 356 записывает `str(ex)` и traceback в logger, затем возвращает `str(ex)` клиенту как internal error.

Проба с 600 синтетическими нечисловыми суммами: **HTTP 500, JSON-RPC -32603, ответ 152 417 символов; захваченный лог 301 636 символов**. Исходный маркер суммы присутствует и в ответе, и в логе. В досье сохранены только размеры и признаки наличия маркера, без полного сырого лога. Это подтверждает выдачу содержимого в logging; фактическую долговременную retention production-логов аудитор не измерял. Без устранения такой выдачи заявлять Zero Durable Storage для нового пути нельзя.

**Условие закрытия:** отдельно обрабатывать ошибки входа, ограничить их количество и общий размер, исключить исходные финансовые значения и секреты из ответа/логирования. Непредвиденная ошибка должна содержать безопасное сообщение и correlation ID. Повторить пробу 600 ошибок и пробу чувствительного строкового значения: контролируемая validation/tool error, ответ не более ранее принятого бюджета 8 000 символов, отсутствие входных значений в логах. Не переносить лимит Actions 100 000 символов на MCP как универсальное требование протокола; здесь нарушен собственный принятый контроль ошибок сервиса.

### R58-3 — P1: MCP сообщает ложные финансовые результаты

`format_mcp_conversion_text()` на строке 187 читает `financial_summary`, хотя канонический ответ содержит `summary`. Дополнительно используются неверные имена `total_transactions`, `earliest_date`, `latest_date` вместо `transaction_count`, `date_from`, `date_to`.

На двух реальных синтетических строках −189,50 и +3 400,00 EUR MCP возвращает **0 проводок, расходы 0.00, доходы 0.00, сальдо 0.00, период N/A**, хотя скачанный CSV корректен и сальдо равно **+3 210,50 EUR**. Тест успеха проверяет только наличие фразы и ссылки, поэтому проходит.

Дополнительные ошибки представления: банк подменяется на `Bank`; BMD получает DATEV-название ссылки и DATEV-инструкцию; Abflüsse/Zuflüsse ошибочно обозначены Soll/Haben банковского счёта. Formatter также отбрасывает `notes`, включая раскрытие отдельной privacy-границы OpenAI. В manifest и tools/list вновь появилось недоказанное `zertifizierte`, несмотря на открытый внешний бухгалтерский sign-off.

**Условие закрытия:** отображать канонические поля без подстановки нулей при нарушении контракта; для примера подтвердить 2 строки, −189,50 / +3 400,00 / +3 210,50 EUR и правильные даты. Использовать Abflüsse / Zuflüsse / Saldo; сверить DATEV и BMD отдельно. Вернуть раскрытие RAM TTL и независимой политики хранения AI-клиента, убрать неподтверждённую сертификацию. Проверить также описание тарифов: Starter имеет 20 выписок, а не безлимит.

### R58-4 — P1: опубликованная схема не позволяет использовать заявленный replay

`tools/list` не объявляет `request_id`. При этом `session_id` описан как средство идемпотентности. Канонический обработчик без `request_id` намеренно создаёт новую операцию со случайной частью ключа.

Локально два идентичных tools/call с валидным Bearer Starter и одинаковым session_id возвращают **разные download ID и две COMMITTED-записи по одной единице**. Контрольная проба с добавленным, но не объявленным `request_id` возвращает идентичный ответ. Следовательно, ядро replay работает, однако объявленный MCP-контракт его не обеспечивает.

**Условие закрытия:** объявить стабильный operation `request_id`, объяснить повтор одной операции и новое обращение, синхронизировать JSON Schema с ограничениями канонической модели. Повторить через MCP последовательность A → Replay → B: одна единица у A, тот же файл при Replay, отсутствие доступа к ответу A и списания у исчерпавшего квоту B. Проверить payload mismatch → conflict и eviction → 410 без повторного парсинга/списания; сохранить машинные результаты. JSON-RPC `id` не подменяет operation ID.

### R58-5 — блокер совместимости: legacy manifest и неполный MCP transport

Текущий `schema_version: v1`, `name_for_model`, `api.type: openapi` в `/.well-known/ai-plugin.json` не является доказательством современного installable Plugin. Актуальная упаковка использует корневой `plugin.json` / `mcp.json` либо поддерживаемую `.codex-plugin/plugin.json`-схему; для серверного подключения предусмотрена регистрация MCP URL. Выбрать и испытать конкретный поддерживаемый способ распространения. [OpenAI: Package your plugin](https://developers.openai.com/plugins/build/plugins), [Quickstart](https://developers.openai.com/plugins/quickstart).

Production MCP для OpenAI должен поддерживать Streamable HTTP. Здесь GET с `Accept: text/event-stream` возвращает 200 application/json с диагностикой, notification возвращает 204, неподдерживаемый `MCP-Protocol-Version` игнорируется. Для Streamable HTTP GET должен предоставлять SSE либо отвечать 405, принятая notification — 202 без тела, неподдерживаемая версия заголовка — 400. SSE не обязателен для каждого POST-ответа; JSON-ответ и отсутствие stateful session допустимы. [OpenAI: Build an MCP server](https://developers.openai.com/plugins/build/mcp-server), [MCP: Streamable HTTP](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports).

Само согласование версии 2024-11-05 вместо запрошенной 2025-06-18 допустимо, если клиент поддерживает fallback. Однако соответствующего старого HTTP+SSE-транспорта здесь также нет. Номер версии не доказывает совместимость. [MCP: старый транспорт](https://modelcontextprotocol.io/specification/2024-11-05/basic/transports), [Version negotiation](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle).

Локальные дополнительные пробы: `jsonrpc: 1.0` отражается в успешном ответе; массив вместо объекта params даёт plain HTTP 500; произвольный Origin принимается. Неиспользуемая модель `McpRpcRequest` не валидирует реальный envelope.

**Условие закрытия:** реализовать и проверить поддерживаемый транспорт (предпочтительно официальным MCP SDK); валидацию JSON-RPC envelope, типов params/arguments/id, версии и Origin; корректные protocol/tool errors и notifications. Диагностику вынести с MCP GET на отдельный health/status URL. Пройти MCP Inspector или эквивалентный реальный SDK-клиент, затем actual OpenAI Plugin connection E2E. Для платного пользовательского подключения требуется поддерживаемая OAuth-модель; передача JWT через `license_key` в аргументах модели не является заменой account linking. Анонимный synthetic demo может приниматься отдельно и не подтверждает платный публичный канал. [OpenAI: Authentication](https://developers.openai.com/plugins/build/auth).

### R58-6 — недостаточная привязка production-сборки и E2E

В предоставленном пакете отсутствуют новый полный Image ID / Container ID и манифест связи backend 1.0.16 с проверенным Git. Прежние артефакты 1.0.15 не распространяются автоматически на новый модуль. Более того, закоммиченный `docker-compose.prod.yml` всё ещё задаёт **image 1.0.15 и VERSION=1.0.15**, хотя публичный health сообщает 1.0.16. Это подтверждает рассогласование reproducible deploy configuration, а не подмену контейнера.

**Условие закрытия:** согласовать compose и release version; предоставить санитизированный inspect без секретов, полный image/container ID, Git release commit, пофайловую сверку полного backend-пакета и фактические лимиты JWT/входа/контейнера. После исправлений повторить полную регрессию и адресные MCP-пробы на одной сборке. Представить воспроизводимый acceptance runner и трассу настоящего Plugin-клиента с input, result, CSV-сверкой и ledger; HTTP smoke через собственный скрипт не заменяет эту трассу. Не сохранять ключи, JWT и реальные клиентские данные в артефактах.

## 3. Изменённый Chrome UX: отдельное замечание U58-1

В `extension/app.js:179` docking вызывает `sidePanel.open()` после callback storage и дополнительного await. Успех открытия не контролируется перед закрытием вкладки: `window.close()` на строке 188 выполняется и после исключения, и при отсутствии API. Проба фактического handler в Node VM подтвердила оба пути. Это не воспроизведение в настоящем Chrome и не доказательство обязательной потери user gesture, но unconditional close является установленным дефектом.

**Перед выпуском изменённого extension-пакета:** закрывать вкладку только после успешного docking; при отказе сохранять доступный интерфейс и сообщать ошибку. Испытать sidepanel → tab → sidepanel, отказ открытия, сохранение preview и очистку локальных данных в установленном Chrome. `sidePanel.open()` требует user gesture. [Chrome: Side Panel API](https://developer.chrome.com/docs/extensions/reference/api/sidePanel).

Синтаксическая проверка `node --check extension/app.js` прошла. Backend-тесты не являются UX-приёмкой. Новые SVG/PNG и анимация не имеют подтверждённого здесь визуального sign-off и не закрывают протокольные блокеры.
