## 2. Закрытие условий Решения 52

### R52-1 — изоляция владельца: принято

Платное пространство кэша включает tenant из проверенной личности. В значении сохранён owner scope и добавлена проверка его совпадения. Анонимное пространство отделено от платного.

Подтверждено:

- Tenant A получает 200.
- Tenant B с теми же request ID/payload и исчерпанной квотой получает 429, без ответа и download ID A.
- Анонимный клиент с исчерпанным demo-лимитом получает `limit_reached`, без платного результата.
- Дополнительная положительная проба: два допущенных платных tenant с одинаковыми ID/payload получают два разных download ID и две отдельные COMMITTED-резервации по одной единице.

Анонимный client session остаётся мягким demo scope, не подтверждённой личностью и не устойчивой пользовательской квотой. Это соответствует ранее принятому ограничению demo-режима.

### R52-2 — admission и replay до parser: принято

Lookup и квотное решение перенесены до дорогостоящей обработки. Размеры, даты и base64 предварительно проверяются в памяти.

Подтверждено настоящим supervisor:

- File-цепочка **200 → 200 → 410** вызывает парсер **один раз**; ответ успешного повтора побайтно совпадает с исходным.
- Исчерпанный Starter для raw и file даёт 429: **0 вызовов парсера**.
- Свежий RESERVED даёт 409: **0 вызовов парсера**.
- Изменённый raw payload под прежним request ID даёт 409: **0 новых вызовов парсера**.

Новые задачи допускаются через квотный сервис; error paths освобождают только собственную RESERVED, не повреждая прежние COMMITTED. Extended-проба RELEASED после исчерпания сохраняет отказ 429.

### R52-3 — доступность файла при replay: принято

Replay проверяет существование referenced file-entry. При отсутствии файла удаляет dangling operation-entry и возвращает 410 до нового parsing/export.

Прежняя проба на 150 строк без inline base64 после отдельного вытеснения файла теперь получает **410**, без успешного ответа с неработающей ссылкой. Полная очистка dedicated cache также приводит к 410 для завершённой платной операции.
