# Решение 61 — BMD Bankauszug CSV и профили Erste Austria / Erste Visa

Дата: 2026-11-12. Проверенное дерево: `b6c706c8cbef2d57be802c0bd5d736ae612fd392`.

**Вердикт: GO с условиями на реализацию Варианта А. Это не Production GO и не подтверждение успешного импорта в BMD.**

Основание: архитектурное предложение инженера, просмотр текущего кода и первичных технических источников. Именованные реальные CSV не обнаружены при поиске в рабочем проекте; исходные PDF и скриншот ошибки в этой ревизии непосредственно не исследовались. Их содержание, число операций и контрольные суммы ниже — входные сведения отчёта, которые требуется подтвердить при приёмке. Реализация, деплой и изменение реальных банковских данных в рамках этой ревизии не выполнялись.

## 1. Контракт форматов — утверждён

| API-ключ | Содержание | Кодировка | UI |
|---|---|---|---|
| `datev` | Существующий DATEV EXTF Buchungsstapel | Windows-1252 | DATEV — EXTF Buchungsstapel |
| `bmd_bankauszug` | Новый профиль Bankauszug, ровно 22 колонки | UTF-8 с BOM | BMD — Bankauszug CSV, 22 Spalten |
| `bmd_ntcs` | Явный ключ прежнего 8-колоночного экспортера | Windows-1252 | BMD NTCS — bisheriges 8-Spalten-Profil |
| `bmd` | Сохранённый совместимый ключ прежнего 8-колоночного экспортера | Windows-1252 | Отдельно не показывать |
| `muster_csv` | Существующий 6-колоночный экспорт | Существующая Windows-1252 | Сохранить в API |

1. **Не переназначать `bmd` на 22 колонки.** В `main.py:200,396` и GPT Action этот ключ уже имеет действующий смысл. Новый BMD-пункт интерфейса отправляет `bmd_bankauszug`; для BMD-сценария он является основным выбором. Значение API по умолчанию `datev` не менять.
2. Ввести единый реестр форматов: ключи/алиасы, exporter, encoding, media type, filename, ограничения. Нормализацию алиасов выполнять до вычисления хэша и выбора кэша. Сохранить воспроизведение существующих операций `bmd`: наиболее простой внутренний идентификатор старого профиля — прежний `bmd`, с нормализацией `bmd_ntcs -> bmd`.
3. Новый файл именовать, например, `BMD_Bankauszug_22.csv`; существующее имя файла ответа `bmd` оставить совместимым. MIME нового файла — `text/csv; charset=utf-8`, BOM находится в байтах. Не наследовать Windows-1252 из общей ветки replay.
4. `json` остаётся диагностическим представлением канонической модели. Новые ключи документировать в изменяемых API. Расширение GPT/MCP этим решением не требуется; их существующий `bmd` сохраняет прежний смысл. Если новые форматы там всё же публикуются, одновременно обновляются схемы, инструкции и тесты маршрутизации.
5. Названия «официальный универсальный BMD-формат», «BMD NTCS 5.1 Standard» и сертификация не подтверждены представленным контрактом. 22 колонки — профиль для конкретной маски Bankauszugsverbuchung; 8 колонок — существующий профиль приложения. BMD подтверждает поддержку CSV разных банков, но это само по себе не спецификация данных 22 колонок: [официальное описание BMD](https://shop.bmd.com/ecommerce/product?product_id=195880).

## 2. Каноническая модель и правила извлечения

### 2.1. Поля и происхождение

Добавление `partner: Optional[str] = None` одобрено. Поле должно пройти весь путь parser → registry → supervisor IPC → canonical JSON → exporter/preview. Одного изменения Pydantic-модели недостаточно. Использовать существующий `value_date`, который сейчас не заполняется в `_raw_to_canonical`.

`account_id`/IBAN владельца счёта и IBAN контрагента — разные сущности. Колонку 4 нельзя заполнять IBAN из шапки выписки. При отсутствии надёжного источника она остаётся пустой; при реализации её извлечения добавить отдельное типизированное поле `partner_iban`. Аналогично, оригинальную валюту/сумму хранить отдельно от проводки в валюте счёта, если они извлекаются. Не восстанавливать их приблизительно по курсу.

Контрагент не всегда является второй строкой: там могут находиться адрес, ссылка, комиссия, IBAN или продолжение назначения. Нужна профильная классификация; неизвестное значение — `None`. Для новых профилей разделять назначение и контрагента так, чтобы их конкатенация колонками 2+3 в BMD не дублировала имя. Сохранять полное исходное содержание можно в ограниченном RAM-представлении, не в постоянном журнале.

### 2.2. Профили вместо расширения универсального regex

Выделить `ErsteBankAustriaParser` и `ErsteVisaCardParser` либо эквивалентные изолированные профили; выбирать их по содержимому и структуре документа до универсального fallback. Совпадение только по имени файла или слову Sparkasse недостаточно. Если профиль уверенно распознан, но извлечение неполно, нельзя молча принять более слабый универсальный разбор.

Разбор должен учитывать страницы, строки/координаты и состояния «метаданные → операция → продолжение → итог/новая выписка». Не выбирать последнюю денежную подстроку из всего блока: именно такая логика сейчас находится в `amex_parser.py:521`.

**Даты:**

- У Visa использовать `Buchung` как `booking_date`. `Kauf` — дата покупки, её нельзя без основания называть `value_date`.
- В банковском PDF колонка, названная `Valuta/Value`, означает дату валютирования. Сохранять её как `value_date`; дату проводки брать только из подтверждённого источника.
- Если отдельной даты проводки нет, автоматическая подмена запрещена. Допустим явно обозначенный режим «Valutadatum als Buchungsdatum», подтверждённый PO/бухгалтером, с отметкой происхождения и предупреждением в результате. До такого согласования отсутствующий `booking_date` блокирует бухгалтерский экспорт, но не диагностику.
- Проверять календарную валидность, високосность, переход декабря/января и год из конкретного сегмента выписки. Не подставлять текущий год/дату и не угадывать неоднозначный формат.

**Суммы и границы блоков:**

- Суммы считать в целых центах/Decimal; в JS — безопасные целые значения с проверкой диапазона. `72,00-`, `4,38 -`, `1.000,00`, NBSP и поддерживаемые варианты минуса нормализовать по профилю. Конфликт знаков/невалидное число — ошибка, а не `0`.
- Брать сумму из денежной колонки проводки. FX-курс `1.1567`, иностранная сумма `0.64`, номер документа и дата не являются EUR-суммой операции.
- `Offener Betrag`, `Einzugsbetrag`, `Umsatz der Karte`, остатки и служебные строки завершают блок, а не дополняют последнюю операцию.
- `Abschlussbuchung` без суммы не создаёт проводку; следующие шесть комиссий разбираются отдельно. Если дата наследуется от группового заголовка, правило должно быть подтверждено структурой документа и протестировано.
- Частичное извлечение нельзя скрывать успешным результатом: неразобранные строки области операций и неоднозначные суммы отражаются в диагностике и блокируют бухгалтерский экспорт. Известные служебные строки классифицируются отдельно. Две реальные одинаковые операции нельзя удалять по совпадению даты, суммы и текста.

### 2.3. Остатки и объединённые выписки

Балансовая сверка — проверка `opening + movements = closing`, а не доказательство правильности всей двойной бухгалтерской записи или контировки.

Для PDF 029–034 сначала выделить логические выписки, которые могут занимать несколько страниц. Проверять одинаковый счёт/валюту, последовательность периодов, отсутствие пропусков/наложений и связь остатков соседних сегментов. Только после этого использовать первый начальный и последний конечный остаток для общей сверки. Простое «первая страница + последняя страница» недостаточно.

Текущий `main.py:285–290` перезаписывает остатки одного счёта при каждом новом файле. При поддержке нескольких файлов того же счёта это место необходимо заменить проверенным объединением сегментов либо явно отклонять неподдерживаемое объединение. Порядок загрузки файлов не должен определять остатки.

Контрольные значения из отчёта:

- Bank: 12 операций; `47166 + 46276 = 93442` цента.
- Visa: 5 операций; `-29483 + 29483 - 438 - 4858 - 4300 - 1773 = -11369` центов. Чистое движение `+18114` центов; перечисление/погашение `+29483` учитывается один раз, итог `113,69` не создаёт дополнительную операцию.

Отсутствующие остатки дают `UNVERIFIED`, не `BALANCED`. Нельзя подгонять знак или сумму последней операции для достижения нулевой разницы. Смешение разных счетов/валют сохраняет существующие ограничения экспорта.

### 2.4. OCR

Удаление `or total_pages > 0` в `amex_parser.py:278` одобрено. Для обычного текстового PDF с неизвестной структурой отсутствие операций не означает необходимость OCR.

Порог `<50` для всего документа допустим как адресное исправление, но не как полная поддержка смешанных PDF. Страница-скан внутри текстового документа не должна молча пропускаться: обнаружить неполноту и вернуть явную диагностику либо применить ограниченный OCR по страницам. Сохраняются C07, ресурсные лимиты и жёсткое завершение процесса; `ThreadPoolExecutor.result()` без собственного дедлайна не является защитой от зависания.

## 3. Контракт нового CSV

Заголовок фиксируется дословно:

```text
Transaction Booking Date;Transaction Purpose;Transaction Partner;Transaction Partner IBAN;Transaction Foreign Currency;Transaction Foreign Amount;Transaction Currency;Transaction Amount;Booking Amount;Invoice Type;Invoice Currency;Invoice Total;Invoice Number;Invoice Internal No;Invoice Date;Invoice Partner Company;Invoice Partner Number;Invoice Document ID;Invoice File;Invoice Tags;Transaction ID;Payment Category
```

- Ровно 22 поля в заголовке и каждой записи; не собирать пустые хвосты вручную. Если заполнены первые девять полей, остаются **13 пустых полей**, включая последнюю колонку.
- Один UTF-8 BOM в начале; `;`, CRLF, `QUOTE_MINIMAL`, удвоение кавычек. Контракт окончания строки фиксируется golden-тестом. Для текстов этого профиля нормализовать внутренние CR/LF в пробелы, чтобы одна операция оставалась одной физической строкой; `;` и кавычки сохраняются через CSV-экранирование.
- Дата `DD.MM.YYYY`, сумма со знаком минус только для списаний, две цифры после запятой, без тысячных разделителей. Нулевые суммы выводить `0,00`, не `-0,00`.
- Для подтверждённых EUR-проводок в EUR-счёте колонки 8 и 9 равны. Для иных валют равенство нельзя предполагать: первый релиз ограничить подтверждённой семантикой валюты счёта; неподдерживаемый FX-сценарий отклонять явно. Колонки 5–6 заполнять только при надёжном извлечении оригинальной валюты и суммы.
- Поля Invoice/metadata остаются пустыми, если нет соответствующих исходных данных. Не выдавать внутренний UUID операции за исходный Transaction ID банка.
- Формульная нейтрализация применяется к недоверенным текстовым значениям, включая будущие reference/metadata поля; учитывает опасные префиксы и начальные управляющие символы. Она не должна менять типизированные отрицательные денежные значения. Одних кавычек недостаточно. Выбранное экранирование текстов проверить реальным BMD-импортом: апостроф может стать видимым символом назначения.

Основания: [Python csv](https://docs.python.org/3/library/csv.html) описывает управление dialect/quoting/newline; [CWE-1236](https://cwe.mitre.org/data/definitions/1236.html) описывает исполнение формул из недоверенных CSV-ячеек. Это не подтверждение совместимости конкретной маски BMD.

## 4. UI, кэш и квота — обязательное согласование

1. Выбор трёх форматов до старта одобрен. В превью отображать фактический формат результата. При переключении старый download отключается до готовности нового; поздний ответ предыдущего запроса не должен менять текущий выбор. Ошибка не должна оставлять файл с новым названием и старым содержимым.
2. **Предпочтительный поток: одна проверенная каноническая конвертация → превью и несколько экспортных представлений.** Превью строится из canonical, а не угадывается по расширению `.csv`. Для существующих CSV/истории допустим форматный адаптер с полноценным CSV-разбором; `split(';')` и построчный regex не покрывают quoted records.
3. У серверного пути канонический результат хранится в ограниченном RAM-кэше с текущим Web/Extension TTL 600 секунд, привязанным к tenant и операции. Переключение формата использует этот результат и не продлевает TTL. Не сохранять исходные PDF/новые копии canonical на диск или в историю расширения для обеспечения переключения.
4. **Квота списывается за исходную успешную обработку, не за каждое представление.** Сейчас `main.py:229` включает формат в `request_hash`: тот же idempotency key с новым форматом конфликтует, новый key запускает новую резервировку. Поэтому повторный POST при переключении без изменения контракта не одобрен.
5. Разделить идентичность оплачиваемой операции и ключ представления `(tenant, operation, format, export-options, exporter-version)`. Операция привязана к исходным файлам и параметрам разбора. Новый формат может отличаться; другой исходный payload не может присоединяться к старой операции. Доступ к результату требует проверки владельца и действующей авторизации; по истечении RAM-результата — явное сообщение/410 и новый пользовательский запуск, без скрытого повторного списания. Существующий контракт повторов старого API не ломать: изменение вводится расширением API/ответа, а не удалением формата из старого хэша.
6. Текущий `main.py:332–333` фиксирует квоту до экспортных проверок. Для нового потока определить точку успеха и применять её последовательно: запрос бухгалтерской конвертации, отклонённый из-за неполного разбора/дисбаланса/ошибки экспорта, не оставляет новое успешное списание. Диагностический `format=json` имеет отдельно документированную семантику. Нельзя исправлять это освобождением ранее COMMITTED операции при ошибке повтора.
7. Общий валидатор допуска экспорта обязателен и для серверного, и для локального пути. Получение `format=json` не должно превращаться в обход запретов экспорта на ошибки, смешанные счета/валюты или неподдерживаемый DATEV-период.
8. Offline поддержка одобрена как явно выбранный режим. Ошибка Managed API, отказ авторизации, квоты или серверная недоступность не должны запускать тихий локальный fallback. Общие JS-парсеры/экспортеры использовать в Chrome и Firefox из одного источника сборки; проверять оба пакета.
9. Для локального Windows-1252 необходим настоящий encoder, а не UTF-8 `TextEncoder` с другим MIME. Для нового BMD — настоящий UTF-8 BOM. Скачивание использует подготовленные байты: нельзя повторно собирать cp1252-файл из JS-строки через обычный Blob. Непредставимые символы не заменять незаметно в новых реализациях; показать ошибку/предупреждение по явно принятой политике.

## 5. Приёмка и границы разрешения

| Группа | Обязательное доказательство |
|---|---|
| Совместимость | Старые `datev`, `bmd`, `muster_csv` сохраняют контракт; `bmd_ntcs` даёт тот же старый exporter; неизвестный формат не превращается в DATEV |
| Bank | Синтетический PDF с геометрией шести страниц/сегментов, 12 операций, все шесть комиссий, контроль каждой строки, остатки и цепочка 029–034 |
| Visa | Пять операций, правильная вторая дата, сохранённое погашение, FX не меняет EUR-суммы, итоги не превращаются в операции |
| Отрицательные случаи | Недостающая/дублированная страница, другой IBAN, разрыв остатков, другой год, високосная дата, неоднозначная сумма, одинаковые реальные платежи, скан среди текстовых страниц |
| CSV | 22 колонки, точный заголовок, один BOM, CRLF, umlauts/ß, `;`, кавычки, пустые поля, знаки, формульные строки, отсутствие выдуманного IBAN/FX |
| UI | Landing/Chrome/Firefox; выбор до старта и после; три последовательных переключения, отмена/гонка ответов, ошибка и восстановление; проверяются скачанные байты, не только надпись |
| Квота/изоляция | Одна конвертация и три формата не дают трёх списаний; конкурентные повторы; ошибка до успеха; повтор после TTL; другой tenant; отказ Managed не включает fallback |
| Backend/offline parity | Одинаковые canonical-значения и экспортная семантика на общих фикстурах; динамическое время EXTF фиксируется в тесте |
| OCR/C07 | Текстовый неподдерживаемый PDF не запускает OCR; скан/смешанный PDF не теряет страницы; зависший worker завершается в пределах бюджета |
| Внешний BMD sign-off | Точная версия NTCS, маска/Bankauszugskreis и mapping, пропуск заголовка, 12 и 5 операций, даты, назначения, знаки, суммы и остатки; отсутствуют нулевые подстановки и лишние строки |

Фикстуры создавать синтетически с сохранением структуры/геометрии, а не только заменой видимого имени в реальном PDF. Проверить скрытый текст, metadata, изображения, IBAN, идентификаторы и логи. Вымышленный IBAN для положительного теста должен быть структурно и по checksum валиден; намеренно невалидный — отдельный отрицательный тест. Реальные материалы остаются вне git и общедоступных артефактов.

Разрешено начинать реализацию нового экспортера, профильных парсеров и UI в рамках этого контракта. Обязательные условия перед выпуском: разрешённая семантика даты Valuta/Booking, реализованное переключение без повторной квоты, полный регрессионный набор и реальный sign-off бухгалтера в её BMD-профиле. Закрытые смежные этапы не переоткрываются; изменение их поведения проверяется регрессиями.
