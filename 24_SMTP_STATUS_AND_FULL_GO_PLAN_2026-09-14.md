# Решение 24 — SMTP-OTP и порядок приёмок Full GO

Дата: 2026-09-14. Основания: отчёт PO/Antigravity в переписке, решения 16 и 23. Проверены локальные материалы; отдельного SMTP-evidence-пакета в docs при поиске не найдено. Отправка писем, чтение почтового ящика и независимый серверный прогон не выполнялись.

## 1. Статус SMTP

**Положительная функциональная цепочка SMTP-OTP принимается по подтверждению PO как получателя:** request-code → реальное получение письма → обмен кода на JWT → авторизованная конвертация 200. Это закрывает прежний пробел «доказана только ошибка доставки 502, успешная доставка отсутствует».

Это не независимая проверка DNS/Resend или полная повторная приёмка Managed Auth. Для архивирования достаточно одного краткого протокола с временем, commit/image, идентификатором письма у провайдера, обезличенными статусами запросов и подтверждением получателя. Не сохранять OTP, JWT, SMTP/API-секреты. Повторять успешную отправку только ради документа не требуется, если эти сведения доступны по уже выполненному тесту.

Установленное расширение → OTP → конвертация → logout/отказ старого токена остаётся отдельной интеграционной цепочкой, если ранее не подтверждено для выпускаемого пакета. Не считать ручные API-вызовы доказательством прохождения UI расширения. Ранее принятые отрицательные проверки OTP/lockout не переоткрываются без изменения соответствующего кода.

## 2. Следующий инженерный приоритет

**A — Stripe Lifecycle: следующая активная инженерная приёмка. B — фактический DATEV/BMD-импорт: назначить проверяющего и время уже сейчас, выполнять параллельно при наличии специалиста. C — организационный контур: начать одновременно, не откладывать до конца.**

Stripe проверять в sandbox с синтетическими данными. Цепочки: Starter, PRO и Lifetime; разрешённые Price ID/валюта/сумма; выдача entitlement после подтверждённой оплаты; продление и период квоты; неуспешная/отложенная оплата; окончание/отмена подписки; refund; повторные и переставленные webhook-события; неверная подпись; привязка покупки к нужному tenant. Проверять итог в БД и фактический доступ/лимиты API, а не только HTTP 200 webhook. Отмена в конце периода и немедленное прекращение проверяются как разные состояния согласованной продуктовой политики. Test-mode результат не объявлять проверкой live Payment Links: производственный каталог сверить отдельно без обязательной реальной покупки.

DATEV/BMD: цель — успешный импорт в реальные целевые версии программ с подтверждением бухгалтера. Для поддерживаемых пилотных профилей сохранить синтетический вход, ожидаемые проводки, выходной файл и протокол импорта/сверки. Проверить суммы, даты, валюту, S/H, счета, финансовый год и баланс. Структурная валидность CSV сама по себе недостаточна. Область общего допуска можно ограничить реально принятыми профилями и экспортами.

Организационный контур: актуализировать ранее согласованные Hosting/Privacy/AVV-материалы под фактическую цепочку Hetzner, Resend и ImprovMX и реальные категории передаваемых данных. Ответственный за юридическую приёмку должен подтвердить комплект до клиентского пилота. Настоящее решение не является заключением о юридической достаточности документов или трансграничных гарантиях провайдера.

## 3. Что ещё не следует потерять

C07 остаётся закрытым по Решению 23. Решение 16 отдельно сохраняло подтверждение установленного Managed-flow, revocation при worker/DB-ошибках и миграции предусмотренной БД. Проверить наличие последующих закрывающих протоколов; при их отсутствии провести адресную приёмку. Это список неподтверждённого объёма, не утверждение о наличии новых дефектов.

## 4. План ближайшего рабочего дня

1. Архивировать обезличенное подтверждение уже выполненного SMTP-теста и обновить таблицу статусов приёмки.
2. Выполнить Stripe sandbox end-to-end, собрать event IDs, итоговые entitlement/quota и результаты API; зафиксировать фактические сбои для исправления.
3. Передать бухгалтеру минимальный комплект DATEV/BMD и согласовать импорт; назначить ответственного за организационные документы.
4. Проверить оставшиеся Managed-flow/revocation/migration evidence и составить единую короткую таблицу: принято / ожидает проверки / дефект, с владельцем и ссылкой на доказательство.

**Итог: успешная доставка SMTP-OTP принята по свидетельству PO; следующий инженерный этап — Stripe Lifecycle. Общий Full GO ещё не выдан.**
