## 3. F02 — P1: хэш не однозначно связывает операцию с фактическим входом

### 3.1. Разный порядок выбора источника данных

В `compute_payload_hash` (`gpt_action.py:273–299`) после structured-данных сначала выбирается `raw_content`, затем `file_base64`. Фактическое чтение использует обратный порядок: сначала файл, затем raw content.

Проба с одним `request_id`, постоянным `raw_content` и двумя разными base64 CSV получила:

- Одинаковые `request_hash`.
- Два HTTP 200 с разными итогами: **-10 и -20**.
- Одну COMMITTED-резервацию на **1 единицу**.

Таким образом, исходный обход «разные выписки по одной резервации» сохраняется при совместной передаче двух источников. Это не коллизия криптографического SHA-256: в него подаётся один и тот же неверно выбранный источник.

### 3.2. Неоднозначная сериализация параметров

Поля export format, account и bank name добавляются в хэш последовательным конкатенированием без обозначения границ. Пара `account=1200, bank_name=a` и пара `account=120, bank_name=0a` дают одинаковый хэш. Под одним request ID оба запроса получили 200 и разные CSV preview, но только одну единицу расхода. Обе строки счёта проходят действующую валидацию.

Кроме того, хэш не включает `value_date` и parser filename. Следует определить полный набор влияющих на результат параметров, а не ограничиться проверенными суммами.

**Закрытие:** выбрать единственный источник (либо отклонять несколько одновременно), использовать его одинаково при хэшировании и обработке. Хэшировать однозначный структурированный объект с именованными полями и всем согласованным набором параметров, без склейки строк. Проверить оба приведённых контрпримера; иной payload под прежним request ID должен получать 409 либо явный отказ за несовместимые источники.

## 4. F02 — P1: RELEASED не является действующим разрешением на повтор

`check_and_reserve_quota` возвращает существующую запись до оценки доступной квоты, независимо от её статуса. Adapter отмечает повтором только COMMITTED (`gpt_action.py:618`), а полученный RELEASED затем коммитит как обычную новую работу (`:689`).

Проверенная цепочка:

1. Контролируемый отказ экспортёра даёт 500 и RELEASED на 1 единицу.
2. Подготовлены 20 COMMITTED единиц того же действующего периода.
3. Новый request ID корректно получает **429**.
4. Повтор прежнего RELEASED request ID получает **200**, переводит его в COMMITTED; суммарный расход становится **21**.

Защита `release_quota` от изменения COMMITTED принимается, но не устраняет этот переход.

**Закрытие:** задать обработку всех состояний. RELEASED-повтор должен заново атомарно получить разрешение по текущей квоте либо быть отклонён по явному контракту. RESERVED должен означать выполняющуюся операцию с согласованным поведением конкурентного повтора, а не разрешение на независимую вторую работу. COMMITTED сохраняется неизменным. Добавить тест RELEASED → исчерпание → retry и конкурентных повторов; лимит не превышается.

### 4.1. Завершённый повтор ещё не возвращает сохранённый результат

Три идентичных запроса одного request ID, включая запрос после очистки download cache, вызвали настоящий экспортёр **три раза** и создали три download ID. Квота списана один раз, но обработка и публикация файла выполняются заново. Для raw/file input парсинг вообще расположен до проверки идемпотентности.

Решение 50 требовало определить возврат завершённого результата и поведение после истечения RAM-кэша. В текущем коде отсутствует связь завершённой операции с сохранённым результатом; DATEV header и имя файла содержат время нового экспорта.

**Закрытие в рамках того же F02:** завершённый повтор при доступном результате возвращает согласованный сохранённый результат без нового parsing/export. После истечения результата — явное документированное поведение (например, результат истёк и нужна новая операция), с контролем квоты и нагрузки. Проверять идемпотентность и доступ до дорогой обработки; не хранить финансовый результат на диске ради выполнения этого условия.

## 5. F03 — P1: число ошибок валидации не ограничено

Новый глобальный `RequestValidationError` handler (`main.py:56–70`) ограничивает каждый input snippet, но возвращает все ошибки. Ограничение успешного ответа в adapter этот путь не охватывает.

Независимый контрпример: **600 коротких строк** с `amount="x"`.

- Входящий JSON: **41 445 символов**.
- HTTP 422, 600 ошибок.
- Ответ: **126 502 символа**.

Это превышает требование Actions менее 100 000 символов на вход и ответ. [Официальные ограничения OpenAI Actions](https://developers.openai.com/api/docs/actions/production).

**Закрытие:** ограничить число возвращаемых ошибок и общий сериализованный размер, при необходимости указывая число скрытых ошибок. Проверить успешные и отрицательные ответы, включая ошибки до входа в endpoint. После сокращения file/preview выполнить окончательную проверку бюджета, а не только повторный подсчёт. Для публичного Action сохранить запас относительно платформенного предела. Добавить приведённую пробу; не отражать содержимое выписки или токены в ответах ошибок без необходимости.

## 7. Допуск к следующему этапу

**Staging clearance: GO в ограниченном объёме.** Допустим отдельный тестовый контейнер/endpoint с собственной синтетической БД и тестовыми credentials, ограниченным доступом и без production-томов. Builder E2E проводится на синтетических выписках; никакой публичный клиентский доступ из этого решения не следует.

**Production deploy clearance: NO-GO** до закрытия остаточных F02 и F03. Исправления проверяются адресными пробами и регрессией затронутых quota/convert путей; полный повтор C07 или Stripe Sandbox не требуется.

Для окончательного G07 сохраняется привязка release commit → image ID → container ID → source manifest и проверка настоящего Custom GPT против именно этой сборки: подтверждённая личность, квота/идемпотентный повтор, отказ и восстановление, ограниченные ответы, реальное скачивание Windows-1252 с контрольными суммами. До публикации дополнительно закрывается документальная часть F05.

**Рабочее поручение:** однозначный payload hash и единственный источник → явные состояния/replay операции → общий error/response budget → адресная повторная приёмка → окончательный G07. Полное закрытие F01–F05 по представленному отчёту не утверждается.

C07, Managed Extension, Synthetic GO, S05 и ранее принятый Stage 2 сохраняют статусы. Stage 1 DATEV/BMD остаётся открытым до внешнего бухгалтерского sign-off.
