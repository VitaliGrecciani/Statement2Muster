## 2. Блокирующие замечания

### R62-1 — P1: реальный UI списывает квоту за результат, который запрещено экспортировать

**Места:** `backend/app/main.py:386–400`; `landing/app.js:365–412`; `extension/app.js:1729–1772`; тест `backend/test_bmd_bankauszug_erste.py:444–483`.

Оба UI используют сначала `POST ...?format=json`, затем GET export. Для JSON проверки экспортной допустимости пропускаются, а `commit_quota` вызывается безусловно. Проба с Erste без Valuta opt-in: POST **200**, `export_eligible=false`, GET BMD **422**, прирост **1 COMMITTED**. Тест инженера сам закрепляет два списания за «без opt-in → с opt-in».

Перенос commit после проверки исправил прямой CSV POST, но не пользовательский поток. То же разделение не позволяет проверить выбранный формат до списания: UI не передаёт целевой CSV-формат в JSON-конвертацию, поэтому форматные ограничения/ошибка сериализации выявляются позже.

**Закрытие:** отделить платную успешную конвертацию с выбранным форматом от диагностического JSON. До commit проверить общие и форматные ограничения и возможность сериализации. Превью с блокирующим результатом не должно автоматически расходовать квоту обычного конвертера. Если диагностика задумана как отдельная платная услуга, это отдельный явно согласованный UX/контракт, а не скрытое поведение кнопки конвертации. Проверить actual UI sequence: запрет/исправление/повтор/три формата, отказ сериализации, ledger до и после. Не освобождать прежний COMMITTED при ошибке повтора.

### R62-2 — P1: нарушена целостность replay и срок жизни операции

**Места:** `backend/app/main.py:248–264,350–411`; `backend/app/services/quota_service.py:93–95`.

Два независимых кэша содержат связанные данные без проверки этой связи:

1. Удалить только canonical operation → POST replay возвращает **200** и прежний operation_id → GET export отвечает **410**.
2. Удалить оба кэша → повтор COMMITTED-запроса возвращает **200**, заново запускает parser и создаёт новый operation_id. Инструментация: `parser_calls=2` вместо 1.

Второй случай возобновляет обработку и TTL старой операции; протокол требует явного истечения, а не скрытого повторного выполнения. Отказ `cache.set` из-за размера также должен обрабатываться, а не выдавать заведомо неработающий operation_id.

**Закрытие:** для COMMITTED без доступного требуемого результата — детерминированный 410 до parser; ссылочная целостность replay/operation; атомарное либо согласованное admission/eviction; никакого обновления committed ledger и TTL при replay. Отдельно проверить restart, eviction каждого кэша и слишком большой результат.

Совместимость rollout также требует решения: новый хэш безусловно дописывает `:False` для старых запросов без opt-in (`main.py:242–247`). Сохранённый старый request_hash будет отличаться и приведёт к 409. Нужен тест прежней записи ledger и явная совместимая стратегия версии хэша.

### R62-3 — P1: локальные экспортеры не соответствуют серверным и теряют контировку

**Место:** `extension/app.js:1379–1411`, соответствующий код Firefox.

Node-проба на canonical transaction с `contra_account='4930'`:

- DATEV metadata имеет **35 полей**, `EUR` находится в **17-м**, 22-е пусто. Серверный контракт помещает валюту в 22-е поле; прочие metadata тоже строятся другим шаблоном.
- `contra_account` теряется в локальных DATEV и BMD — колонка Gegenkonto пуста.
- Старый BMD header меняется с `Satzart;Belegdatum;Konto;Gegenkonto;Betrag;Währung;Text;Belegnummer` на `Satzart;Datum;Konto;Gegenkonto;Betrag;Waehrung;Buchungstext;Belegnummer`.

Успешный тест 22-колоночного JS-exporter не является parity-тестом всех форматов.

**Закрытие:** единый контракт схем и metadata; общие canonical fixtures; сравнение всех колонок/счетов/референсов/ограничений текста для backend и offline всех трёх форматов. Динамическое время фиксировать. Не исправлять сравнение простым исключением всех metadata из проверки.

### R62-4 — P1: повреждённая сумма молча превращается в продолжение предыдущей операции

**Место:** `backend/app/parsers/erste_parser.py:602–614,737–743`.

В текстовом fallback для страницы без определённых координат колонок:

```text
Buchungstext Valuta/Value Beträge/Amounts in EUR
Good 01.09.2026 10,00-
Bad 02.09.2026 12,3X-
```

Результат: **1 операция**, `errors=[]`, описание `Good Bad 02.09.2026 12,3X-`, сумма `-1000` центов. Строка второй операции исчезает как финансовая запись. При отсутствующих остатках независимой защиты сверкой нет: получится UNVERIFIED, а не блокирующая ошибка.

**Закрытие:** строка, похожая на начало операции с датой/денежной колонкой, но имеющая невалидную сумму, должна стать parser error. Разделять продолжение текста и повреждённую операцию, не отправлять оба случая в `extra_lines`. Проверить профиль на text fallback, координатных строках и разнесённых по y частях одной записи; все ветви должны одинаково блокировать неполный разбор.

### R62-5 — P1: последовательность выписок доказана недостаточно, offline выдаёт ложный BALANCED

**Места:** `backend/app/services/reconciliation_service.py:98–150`; `extension/app.js:1839–1889`.

Независимые пробы:

- Два корректных сегмента с одинаковой датой операций: порядок A,B → **BALANCED**, B,A → **DISCREPANCY**. Вторичный ключ сортировки — порядок загрузки.
- Одна и та же выписка с операциями `+100/-100` и одинаковыми начальным/конечным остатками, переданная дважды → **BALANCED**. Совпадение остатков не доказывает отсутствие дубликата/перекрытия.
- Вызов реальной `processClientSideFiles` с двумя синтетическими Erste-файлами, каждый отдельно BALANCED, но первый закрывается на 90 EUR, второй открывается на 200 EUR → общий **BALANCED**, `export_blocks=[]`. Offline только объединяет статусы, не проверяет цепочку.

**Закрытие:** переносить номера/годы/периоды логических выписок и идентичность сегментов через canonical/IPC, проверять дубли, пропуски, наложения и непрерывность независимо от порядка загрузки. Разрешение неоднозначных цепочек — явная ошибка/диагностика, не зависимость от upload order. Реальные одинаковые платежи сохранять, дубли целых выписок выявлять отдельно. Одинаковый контракт на сервере и offline; не объявлять общий BALANCED при непроверенном составе batch.

### R62-6 — P1: поздний ответ восстанавливает файл предыдущей операции после сброса UI

**Места:** `extension/app.js:476–483,1500–1571,2435–2452`; аналогичные жизненные циклы `landing/app.js:196–246,313–346`.

Проба реальной `switchPreviewFormat` с задержанным body: начать BMD export → вызвать `clearFile()` → выбрать DATEV → завершить старый ответ. Наблюдение:

```json
{"selected":"datev","filename":"BMD_Bankauszug_22.csv","downloadEnabled":true}
```

Счётчик защищает только следующий export-запрос. Сброс формы, смена датной политики, начало новой конвертации/демо не инвалидируют весь цикл. Ошибочные ответы дополнительно проверяют seq до `await resp.json()`, но не после него.

**Закрытие:** единое поколение операции для conversion и export, отмена запросов при смене входов/режима/Valuta/выходе из аккаунта/сбросе; проверка поколения после каждого await перед записью состояния. GET export в обоих UI сейчас без AbortController/deadline, поэтому вернуть ограничение времени на headers и body и восстановление интерфейса. Проверить старые success/error ответы, две загрузки подряд и переключение во время первоначальной конвертации в настоящем browser smoke.

### R62-7 — P1: новый export endpoint принимает значение счёта, разрушающее CSV

**Места:** `backend/app/main.py:443,472–477`; `backend/app/exporters/bmd.py` и `datev.py` — ручная интерполяция Konto.

Запрос GET export с `default_bank_account=1200";"EXTRA` возвращает **200**, BMD-заголовок имеет 8 колонок, строка — **9**. Это воспроизведено через ASGI; пользователь управляет параметром нового маршрута.

**Закрытие:** строгая типизированная валидация Konto и Gegenkonto с согласованной длиной/цифровым форматом на всех входах, включая повторный экспорт; корректное CSV-экранирование любых динамических полей. Контрпример должен давать 422 до сериализации, не повреждённый файл.

## 3. Дополнительное условие выпуска

### R62-8 — P2: явная политика HTTP-кэширования финансовых результатов

У успешного нового GET export отсутствует `Cache-Control` (`probe_results.json: export_headers`). RAM-only реализация на сервере сама по себе не запрещает сохранение HTTP-ответа клиентским кэшем.

Добавить `Cache-Control: no-store, private` для CSV/JSON operation responses, проверить эти заголовки через публичный reverse proxy при приёмке. Согласовать общий RAM-бюджет: создан второй кэш с ещё одним полным `RAM_CACHE_MAX_BYTES`; это не общий лимит на две копии результата. Подтвердить допустимый суммарный расход и поведение при отказе admission.

## 4. Доказательная база, которую нужно дополнить

1. Текущая банковская fixture содержит **13**, а не заявленные 12 операций: это явно проверяется в `test_bmd_bankauszug_erste.py:396,454`. Дополнительный кейс одинаковых платежей полезен, но не заменяет отдельную baseline fixture на 12 операций и контрольные `471,66 + 462,76 = 934,42`. Добавить отдельный Visa baseline на пять операций с согласованными остатками, если текущая вариация не совпадает с ним; сохранить расширенные варианты отдельно.
2. Node-тест сравнивает ограниченные искусственные текстовые примеры, а не извлечение обеих PDF тем же pdf.js, который используется в браузере. Нужен browser smoke на синтетических PDF с проверкой скачанных файлов всех трёх форматов, гонок и timeout/recovery для Landing/Chrome/Firefox.
3. `extension_firefox_build/` игнорируется git. Локальная копия изменена, но не является воспроизводимым артефактом коммита. Отличия с Chrome включают старый вывод PRO для любого вошедшего пользователя и отсутствие обновления entitlement display. Нужна сборка из общего источника с объяснёнными платформенными отличиями и хэшами выходных пакетов, а не ручное копирование ignored-каталога.
4. Проверка PII по строковым маркерам не доказывает отсутствие персональных данных вообще. Для синтетических fixtures фиксировать происхождение генератора и проверять metadata/скрытые слои; реальные документы в audit-артефакты не включать. В этой ревизии PII-чистота всего репозитория не сертифицировалась.
5. Зафиксировать исправленную сборку коммитом, повторить регрессию плюс независимые контрпримеры, сопоставить дерево исходников с release artifact. Старые 34/77 PASS не являются подтверждением будущей исправленной сборки.

## 5. Условие повторного решения

На повторный аудит предоставить исправления R62-1–R62-8 с результатами адресных тестов и browser smoke; новые пробы должны проверять ожидаемые безопасные результаты, а не закреплять текущее дефектное поведение. Уже известные внешняя BMD-приёмка и решение PO о default Valuta остаются отдельными условиями и не заменяют технические исправления выше.

Архитектурные ключи остаются прежними: новый `bmd_bankauszug`, старый `bmd`, алиас `bmd_ntcs -> bmd`, существующие `datev`/`muster_csv`. Production GO по представленному рабочему дереву не выдан.
