## 2. Почему остаток R54-1 не закрывается

### 2.1. Несогласованная привязка операции A

В `BUILDER_E2E_TRACE.json` успешному событию A **12:51:36** присвоены `request_id = req_builder_001` и ledger `gpt_req_builder_001`, созданный **12:48:39**. В общем ledger и Markdown для времени **12:51:36.167109** указана другая операция: **`gpt_req_builder_001_fix1`**. Для B заявлен `req_builder_001`.

Таким образом, JSON не устанавливает, какой точный запрос A связан с успешным Builder-вызовом и какую его операцию повторял B. Нельзя подтвердить одинаковые payload/request ID по одному пользовательскому prompt: модель могла изменить параметры Action. Две COMMITTED-записи A с разными ключами сами по себе не доказывают ошибочного двойного списания; они также не доказывают отсутствие списания при Replay.

Есть и несогласованность входа/сводки: новый скриншот показывает prompt с одной операцией **−189,50 EUR**, тогда как JSON успешного A содержит прежние **+3400,00 EUR / saldo +3210,50 EUR**. Без фактических параметров и ответа A нельзя привязать эту сводку к новому сценарию.

### 2.2. Проверяемый Builder Replay по-прежнему отсутствует

Обновлённый JSON содержит только сводку старых анонимных вызовов **12:30:52 и 12:37:02**, одинаковые размеры 2906 байт и заявление об идентичности. Полные успешный/replay requests и responses, их хэши, `download_id`, расход до/после и стабильный `request_id` не добавлены. Три прежних скриншота побайтно совпадают с материалами, уже рассмотренными Решением 55.

Следовательно, прежнее замечание об одинаковых размерах ответов остаётся без адресного исправления. HTTP Replay и локальная проба сохраняются принятыми, но не заменяют Builder-доказательство. Напоминание принятого контракта: без непустого стабильного `request_id` повтор создаёт новую операцию; со стабильным ID и тем же payload работает operation cache. Изменение backend для этого не требуется.

## 3. Единственный оставшийся пакет доказательств

Выполнить и сохранить одну согласованную последовательность в приватном Builder на синтетических данных:

1. **A → 200:** новый стабильный `request_id`, точные параметры Action, успешный response и `download_id`.
2. **A → Replay 200:** тот же ID и payload; тот же download ID и идентичный response; по этой операции остаётся одна COMMITTED-единица.
3. **B → 429:** сменить только короткоживущий тестовый Bearer JWT; отправить точно тот же ID/payload. Сохранить error response без результата A и ledger B до/после без новых резерваций.

В JSON сохранить реальные обезличенные requests/responses либо проверяемые хэши исходных ответов, фактические времена и результаты сравнения. Для ledger фильтровать по **tenant + idempotency key**; ранее созданные две операции A удалять не требуется. Headers Authorization и JWT из артефактов исключить.

Согласовать идентификаторы и сводку в JSON/Markdown с этим прогоном. Исправление обозначений Abflüsse/Zuflüsse в тексте протокола принимается как редактура; оно не подтверждает достоверность сводки нового вызова и не меняет ранее сохранённые скриншоты. Вывод «все условия закрыты» обновить после предъявления указанной последовательности.

Это **оставшееся требование Решения 55**, не новый функциональный gate. Остальные 13 HTTP-сценариев, CSV, JWT, size limits и provenance повторять не требуется. Убедительный пакет может быть компактным: три Action-трассы, сравнение ответов и ledger до/после.

C07, Managed Extension, Synthetic GO, S05 и Stage 2 сохраняют статусы. Stage 1 ожидает внешнего бухгалтерского sign-off. Контролируемая синтетическая приёмка продолжается; публикация GPT Store и реальные клиентские выписки через этот канал данным решением не разрешаются. Production в ходе аудита не изменялся.
