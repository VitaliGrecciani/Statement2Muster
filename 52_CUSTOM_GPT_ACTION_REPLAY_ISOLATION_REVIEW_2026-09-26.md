## 3. R52-1 / F02 — P1: операция в RAM-кэше не привязана к владельцу

В `gpt_action.py:603–613` кэш читается по `op_gpt_{request_id}`. Тот же глобальный ключ используется при записи. Он не включает tenant, а значение не проверяется на принадлежность вызывающему. При cache hit возврат происходит до леджера и demo-квоты.

Независимая проба одного и того же request ID и payload:

1. Tenant A успешно выполняет Starter-конвертацию.
2. Tenant B с отдельным валидным JWT и полностью израсходованными 20 единицами получает **200 и побайтно тот же ответ A**, включая download ID, quota status и ссылку.
3. Анонимный клиент с исчерпанным demo-лимитом также получает **200 и тот же ответ A**, `plan=starter`.
4. Скачать файл по возвращённой ссылке удаётся с 200.
5. Контрольный новый request ID для B даёт 429, для анонимного клиента — `limit_reached`. Леджер B остаётся только с прежними 20 единицами.

Проба предполагает совпадение payload и request ID; произвольное чтение неизвестной выписки без знания payload ею не заявляется. Но идентификатор операции и содержимое запроса не являются подтверждением владельца. Получение результата/ссылки чужой операции и обход admission-контроля через общий кэш — установленный дефект.

**Закрытие:** пространство платного replay должно включать проверенный tenant и ID операции, с проверкой владельца записи перед выдачей. Анонимный режим не может читать платное пространство; ему нужна отдельная политика и пространство ключей. Hash проверяется внутри пространства владельца. Тесты: два tenant с одинаковыми request ID/payload, анонимный запрос после платного, независимые квоты/результаты, отсутствие выдачи чужого download capability. Не менять случайную публичную download-ссылку как продуктовый механизм без необходимости; исправить её несанкционированную выдачу через replay.

## 4. R52-2 / F02 — P1: файловый повтор всё ещё запускает парсер

Replay lookup и auth/quota admission находятся после ingestion. Исправление счётчика экспортёра не подтверждает отсутствие повторного parsing.

Файловая проба с настоящим CSV и supervisor:

- Первичная операция — 200.
- Идентичный повтор с сохранённым cache — 200, ответ идентичен.
- Повтор после очистки cache — 410.
- **Реальных вызовов парсера: 3**, вместо одного.

Таким образом, перед 200 cache hit и даже перед 410 выполняется новый parser job. Это противоречит принятому контракту завершённого replay и позволяет расходовать процессные ресурсы без нового допуска квоты. Аналогично конфликт изменённого файлового payload определяется после дорогостоящего чтения.

**Закрытие:** после проверки размеров и структуры входа вычислить hash, установить подтверждённую личность и разрешённое состояние операции до запуска парсера. Cache hit, hash conflict, выполняющийся RESERVED и завершённая операция с истёкшим результатом не запускают parsing/export. Новый или повторно допущенный RELEASED получает атомарную резервацию до дорогой обработки; ошибки затем освобождают только собственную RESERVED. Добавить реальные file/raw-пробы с подсчётом supervisor calls для повторов 200/409/410 и исчерпанной квоты.

## 5. R52-3 / F02 — согласованность file-entry и operation-entry

File bytes и replay response лежат отдельными записями одного LRU-cache. Они могут вытесняться независимо. Обработчик cache hit не проверяет наличие файла, на который ссылается ответ.

В пробе на 150 строк inline base64 отсутствует. После удаления только file-entry, моделирующего её вытеснение, повтор операции получает **200 с прежней ссылкой**, а GET этой ссылки — **404**. Operation-entry при этом остаётся.

**Закрытие:** перед успешным replay подтвердить наличие доступного результата. Согласовать срок и жизненный цикл response/file: хранить их связно либо проверять ссылочную целостность и возвращать согласованный 410, если доступных байтов уже нет. Отсутствующий файл не восстанавливать новым parsing/export в обход состояния операции. Проверить отдельное вытеснение каждой записи, полную очистку и отсутствие inline-файла.

## 6. F05 и окончательный G07

Публичное техническое раскрытие улучшено и принимается. Оно не подтверждает автоматически наличие DPA для любого consumer OpenAI-аккаунта или правомерность любой реальной выписки. До допуска реальных данных необходимо согласовать выбранный OpenAI-продукт/тип аккаунта и применимые условия нового потока в compliance evidence/registry; в этих внутренних документах соответствующее обновление в данном коммите отсутствует. Прежний Stage 2 GO сохраняется для ранее принятого маршрута.

Даже после устранения R52-1–R52-3 допуск к развёртыванию и полное закрытие G07 остаются разными результатами. Для окончательного G07 нужны release commit → image ID → container ID → source manifest, проверенные health/OpenAPI, а затем настоящий Custom GPT E2E на синтетических данных против именно этой сборки, включая подтверждённую личность, повторы/отказы, скачивание Windows-1252 и контрольные суммы. Условия HTTPS/TLS и платформенного deadline проверяются по [официальным production notes Actions](https://developers.openai.com/api/docs/actions/production).

**Рабочее поручение:** привязать replay к владельцу → перенести admission/replay перед ingestion → согласовать жизненный цикл файла и ответа → повторить адресные пробы и backend-регрессию → запросить production deployment clearance для G07. Полная повторная приёмка C07/Stripe Sandbox не требуется.

C07, Managed Extension, Synthetic GO, S05 и ранее принятый Stage 2 не переоткрываются. Stage 1 остаётся открытым до внешнего DATEV/BMD sign-off. Публичный Custom GPT GO и допуск реальных клиентских данных этим решением не выданы.
