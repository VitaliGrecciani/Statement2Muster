Полное закрытие C07 пока не подтверждено: отсутствуют ранее требовавшиеся OOM-Recovery и Kill/Reap-failure evidence.** Уже принятые A/B, конфигурация Linux и исправление персистентности не переоткрываются.

## 2. Независимая сверка происхождения

Заявленный build commit: `c9482a23004ee7bc7aeea17bfd0ad3bda0c56f8e`.
Заявленный image: `sha256:a08b5c98025262d635ef9cbd51d253f3618e498dc00a6cafe87825960606e346`.
Локальный HEAD на момент этой проверки: `ca2bbb6076c6bddba8d3c38e617d6bff240e2935`. Он не подменял заявленный build commit при сравнении.

Результаты независимой проверки:

- Все 31 хэш контейнерного манифеста совпадают с байтами соответствующих локальных рабочих файлов.
- 21 из 31 совпадают непосредственно с байтами Git blobs build commit; у 10 хэши отличаются.
- После нормализации CRLF → LF все 31 рабочих файла совпадают с соответствующими Git blobs. Отличий содержимого за пределами окончаний строк не обнаружено.
- Следовательно, содержательная привязка к build commit подтверждена; буквальное утверждение «31/31 побайтово идентичны Git blobs» некорректно. Побайтовое совпадение 31/31 относится к рабочему дереву и предоставленному контейнерному манифесту.

Подробности сохранены в [source_comparison.json](docs/audit_c07_v4_review/source_comparison.json). Сам контейнер повторно не считывался: его хэши и image ID взяты из предоставленных файлов.

В V4-скрипте остаётся недопустимый fallback `repo_manifest = container_manifest` при отсутствии внешнего repo-манифеста. Для данного пакета независимая сверка выше снимает неопределённость; этот fallback не используется как доказательство. Для следующих прогонов заменить его на явный FAIL, иначе source_binding_verified может означать сравнение контейнера с самим собой. Это исправление проверочного инструмента, не новый дефект парсера.

## 3. Точный оставшийся объём C07

Раздел 4 решения 19 прямо сохранял OOM-/ресурсный Recovery и Kill-failure. V4 добавил CPU и Cancellation, но не следующие два сценария:

1. **OOM / восстановление под пределом 512 MiB.** Наличие memory.max и CPU-loop не воспроизводят исчерпание памяти. Нужен изолированный тест на идентичном release image/config с подтверждением OOM-события (например, изменением memory.events), исходом worker/API, освобождением ресурсов либо восстановлением сервиса при гибели контейнера и успешным следующим запросом. Проверить сохранность состояния и отсутствие зависшей квоты. Выполнять на тестовом экземпляре с синтетическими данными.
2. **Отказ Kill/Reap.** Нужна контролируемая инъекция отказа в пути супервизора: завершение процесса не подтверждено. Проверить предусмотренный явный ошибочный ответ/сигнал состояния, отсутствие ложного сообщения об успешной очистке и определённый путь восстановления без бесконтрольного запуска новых workers. После пробы обеспечить реальную очистку дочернего процесса. Успешные SIGKILL и crash этого сценария не заменяют.

Не требуется заново менять работающую архитектуру или повторно доказывать все закрытые пункты. Достаточен адресный доказательный пакет этих двух ранее согласованных сценариев, привязанный к фактически запускаемому image и конфигурации.

## 4. Область допуска

**C07: частичная приёмка расширена; формальное полное закрытие отложено до двух сценариев раздела 3.**

Переход к параллельным функциональным проверкам SMTP-OTP на реальной тестовой почте, Stripe Sandbox и DATEV/BMD на синтетических выписках допускается. Закрытие C07 само по себе не означает Full GO для реальных клиентских выписок: сохраняются ранее согласованные функциональные и организационные условия общего релизного решения.
