## 1. Принятый объём

По предоставленным результатам принимаются как частичные доказательства: загрузка Chrome-панели, ввод OTP через UI, конвертация с десятью строками preview, обработка 422, logout с последующим API 401 и очистка списка истории. Отдельный JSON сообщает успешное чтение revocation из SQLite после очистки RAM-кэша и три запуска миграции с сохранением тестовых данных. Без раннеров эти результаты не объявляются независимо воспроизведёнными.

## 2. P1: ошибка revocation-хранилища означает «не отозван»

В backend/app/core/security.py функция is_token_revoked подавляет исключения SQLite через `except Exception: pass`, после чего возвращает False. Отсутствующий DB-файл также приводит к False. decode_access_token после этого продолжает обычную проверку JWT. При пустом RAM-кэше недоступность реестра может позволить криптографически корректному отозванному токену пройти проверку авторизации. Это прямо противоречит критерию Решения 25 об отказе хранилища revocation.

Независимая безопасная проверка выполнена локально: неизменённая функция извлечена через AST; с пустым кэшем и инъекцией sqlite3.OperationalError в connect возвращено False. Ключи, токены и реальная БД не использовались. Это воспроизведение функции, не полноценный HTTP-прогон; успешная конвертация при общем отказе БД не утверждается.

**Исправление:** различать «не найден в доступном реестре» и «проверить невозможно». При недоступном реестре запрещать защищённую операцию с контролируемым отказом, например 503; подтверждённый отзыв даёт 401. Не считать отсутствие файла/таблицы успешным отсутствием отзыва. Проверить HTTP-путь при пустом кэше, недоступной БД и после её восстановления; отозванный токен не должен получать доступ.

## 3. Оставшийся объём Решения 25

- Протокол прямо сообщает получение OTP из Hetzner DB. Это проверяет ввод кода, но не полную установленную цепочку с чтением письма пользователем. Успешная SMTP-доставка ранее принята отдельно; достаточно одного связанного UI-прогона с кодом из письма, без архивирования секрета.
- Проверены UI 422 и API 401 после logout. Не представлены UI-сценарии 401/402/429, отсутствие сети и timeout с восстановлением интерфейса без fallback.
- Не представлены скачанный экспорт и его сверка с выбранным форматом; десять строк preview этого не заменяют.
- Очистка кэша в одном процессе подтверждает SQLite fallback, но не реальный restart/вторую инстанцию. Отсутствуют браузерный restart после logout, повторный вход, DB-failure и применимый worker-failure сценарий.
- Миграционные результаты не содержат последующего входа/конвертации. Добавить эту проверку и сохранить исполняемый раннер.
- Firefox-прогон отсутствует. Он нужен, если Firefox включён в пилот; допустима явная область пилота Chrome-only.
- Очистка списка истории не доказывает очистку всех сохраняемых результатов/preview. Зафиксировать соответствующие storage-ключи и состояние UI без финансовых данных.

Provenance требует уточнения: доклад называет d133bcf, JSON — a2795554249a6f4b0fb2da651308c7e04c5e6f61, протокол — 559dac0/a279555. Указать, какой commit тестировался, что изменилось после него, фактический backend digest и однозначную версию браузера. Тег 1.0.3 не заменяет image digest. Это разрыв трассировки, а не доказательство неверных результатов.
