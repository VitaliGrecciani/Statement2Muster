# Statement2Muster / BankSync DACH — независимый повторный аудит

**Дата:** 2026-09-09. **Объект:** локальные исходники и ZIP v1.0.2 после заявленных R0–R6. **Основание:** [исходный аудит A01–A31](05_AUDIT_2026-09-08.md), ADR-001 и release evidence Antigravity.

**Вердикт: NO-GO для платного релиза и пилота с реальными банковскими документами.** Допустима дальнейшая разработка и изолированная демонстрация на синтетических данных. Утверждение «100% BEHOBEN / все 31 пункта закрыты» не подтверждается.

По исходному смыслу ID: **5 закрыты в проверенном локальном коде; 26 не закрыты полностью — 14 P1, 11 P2, 1 P3**. «Частично» ниже означает, что полезные изменения есть, но критерий закрытия не выполнен. Закрытие локального дефекта не подтверждает публикацию исправления или готовность production.

## 1. Что подтверждено

- Starter на лендинге: €4.90/месяц, до 20 выписок; прежнее обещание безлимита и семидневного trial в карточке убрано.
- Annual-переключатель убран из HTML. Старый JS-обработчик остался, но без DOM-элемента не активируется.
- Лендинг очищает прежний результат перед загрузкой и при ошибке; автоматической подстановки demo вместо неудавшейся конвертации больше нет.
- Дедупликация в основном backend и локальном JS стала недеструктивной.
- Firefox background использует `browser.action.onClicked → browser.sidebarAction.open`; синтетическая проверка обработчика вызывает открытие один раз.
- Реализованы RS256-подпись JWT, ранняя проверка Bearer, проверка Stripe-подписи через SDK, таблица StripeEventInbox, canonical model с integer cents, экспортёры и индикатор reconciliation. Это реальные изменения, но их наличие не обеспечивает заявленные security/business guarantees.
- Все четыре переданных SHA-256 совпали. Каждый файловый entry Chrome ZIP (13 entries) и Firefox ZIP (14 entries) побайтово совпал с соответствующим исходником. Совпадение хешей подтверждает идентичность артефакта, а не его безопасность.
- **18 штатных тестов прошли за 8.35 s** в доступном Python runtime. В `backend/.venv` pytest отсутствует. Использованный runtime содержит FastAPI 0.141.1 / Starlette 1.6.0 / python-multipart 0.0.32, а requirements фиксирует FastAPI 0.110.0. Поэтому это воспроизведение тестов приложения, **не аттестация Docker dependency set**. Версии записаны в evidence.

## 2. Границы и доказательства

Проверены исходники backend, расширений, лендинга, договорных страниц, ADR, эксплуатационных документов и содержимое ZIP. Выполнены локальные ASGI-запросы через httpx, сервисные проверки SQLAlchemy, parser/exporter probes, Node-проверки функций расширения и PDF.js на синтетическом PDF. Большие PDF-бомбы и нагрузочные атаки не запускались: bypass byte budgets проверен уменьшением лимитов в отдельном процессе.

Рабочая `statement2muster.db` не использовалась. Для тестов создавались отдельные SQLite-файлы в evidence; Stripe secret в процессе заменён синтетическим. Billing probes вызывают обработчик на синтетических событиях, **не подделывают production-подпись и не доказывают возможность отправить неподписанное событие в production**. Реальные платежи, рассылки и deploy не выполнялись. Исходники продукта не изменялись.

Не подтверждены: фактическая конфигурация Stripe Dashboard/вебхуков/Price IDs, live deployment и его география, Linux image build, действующий договор с хостером, store moderation, настоящий импорт в DATEV/BMD. Повторное открытие Payment Links через web-инструмент завершилось ошибкой; текущая сверка их href выполнена по локальному лендингу. Последняя визуальная проверка checkout зафиксирована в исходном аудите 2026-09-08. Доказательств новых annual prices нет.

Артефакты: [baseline.txt](docs/audit_2026-09-09/baseline.txt), [Python probes](docs/audit_2026-09-09/probe_reaudit.py), [результаты Python](docs/audit_2026-09-09/probe-results.json), [Node probes](docs/audit_2026-09-09/probe_extension.cjs), [результаты Node](docs/audit_2026-09-09/extension-results.json), [синтетический DATEV](docs/audit_2026-09-09/synthetic-datev.csv). Probes являются воспроизводимыми свидетелями дефектов, а не тестами, чьё успешное завершение означает безопасность продукта.

## 4. Критические инженерные выводы

### 4.1. Identity, квота и Stripe — P1 (A01–A03)

**RS256 подписывает недоказанную личность.** `/api/v1/auth/token` с `{"email":"audit@example.com"}` возвращает 200; повтор с заведомо неверным code возвращает тот же tenant. Следовательно, знание email существующего клиента достаточно для получения его tenant identity; возможность использовать конкретные paid права далее зависит от ошибочного выбора entitlement. `session_id` задаёт клиент; серверной таблицы session/revoke нет. `/auth/jwks.json` возвращает 404, вместо него опубликован PEM endpoint `/public-key`. В production при отсутствии keys код генерирует временные RSA keys вместо отказа старта; mock Stripe defaults также не запрещены.

**Idempotency перепутана с повторным разрешением работы.** Пять POST с разным CSV и одинаковым X-Idempotency-Key вернули 200, в ledger осталась одна единица. Existing reservation возвращается до проверки квоты и независимо от статуса; payload hash не сравнивается; файл парсится заново. Следовательно, бесконечный replay с изменённым телом обходит paid/trial budgets. Два последовательных reserve по 3 единицы до commit одновременно помещаются в trial=3: RESERVED не учитывается. SELECT/flush в длинной request transaction — не атомарный durable reservation; unique constraint tenant/key отсутствует.

**Stripe HMAC исправлен, fulfillment — нет.** Синтетический checkout `mode=payment, amount_total=1, currency=usd, payment_status=unpaid` активирует Lifetime. Повтор того же checkout под другим event ID создаёт второе право. Последующий refund с его payment_intent не отменяет ни одно. Это дефект обработчика валидных событий; возможность внешнего вызова зависит от проверки подписи и настроек production. Определение Starter как ровно 490 cents ломается при налогах/скидках/локализации суммы; все остальные subscriptions становятся PRO. Проверенные Price IDs нигде не используются.

Stripe рекомендует fulfillment с проверкой состояния оплаты и идемпотентностью покупки; asynchronous payment требует отдельной обработки. Порядок webhook deliveries не гарантирован. Текущие updated/deleted/invoice.paid лишь переключают status по пришедшему событию; поздний invoice.paid способен вернуть canceled в active. Нужна сверка текущего объекта Stripe и сохранённого billing period. Источники: [Stripe fulfillment](https://docs.stripe.com/checkout/fulfillment?payment-ui=embedded-form), [Stripe webhooks](https://docs.stripe.com/webhooks).

Ещё один воспроизведённый дефект: после создания trial и добавления active PRO `get_or_create_trial_entitlement` всё равно выбирает trial. `.first()` без приоритета/периода не является решением entitlement. Starter считает rolling 30 days, а не период Stripe; valid_until игнорируется.

### 4.2. Достоверность бухгалтерских данных — P1 (A08, A10–A15)

**Canonical type не подтверждает происхождение значения.** Примеры из probes: неверный amount становится нулём со статусом VALID; строка с 31.02 пропускается без row error; явный USD в `Waehrung` становится EUR; account B превращается в account A. `description` в английском CSV не входит в text aliases. Fuzzy поиск `buchung` может выбрать Buchungstext вместо даты. Generic fallback остаётся, несмотря на декларацию default-deny.

**BALANCED не доказывает полноту.** CSV parser восстанавливает opening как first_saldo − first_amount. Для одной строки closing=first_saldo, поэтому равенство истинно при любом ошибочно распознанном amount. В probe строка `10,00 S` превращена в положительную и объявлена BALANCED. Такой контроль допустим как вывод opening только для верифицированного профиля и порядка строк, но не как независимое доказательство знака/полноты. Нужны независимые statement opening/closing, currency partition, покрытие всех строк и проверка running balances. Сейчас баланс следующего файла того же account перезаписывает предыдущий; суммы агрегируются сразу за оба файла.

**DATEV имеет конкретные семантические ошибки.** Для операции 01.01.2025 header выдаёт Wirtschaftsjahr/период 2026; Belegdatum=0101 теряет год. При Konto=1200 положительное движение банка экспортируется H, отрицательное S. Знак S/H относится к полю Konto: для активного банковского счёта поступление должно увеличивать Soll, списание — Haben. Исправлять нужно согласованную пару Konto/Gegenkonto и направление, а не механически менять знаки для любого будущего профиля. Официальное пояснение: [DATEV — правило S/H и Konto](https://www.datev.de/dnlexom/v2/content/files/st2112692875_de.pdf).

Кроме этого, Berater=1001/Mandant=10001, год и default account задаются без профиля клиента; Gegenkonto пустой. BMD exporter — самописные 8 колонок с названием «5.1»; без согласованной схемы импорта нельзя подтвердить официальный формат. Не утверждается, что любой настраиваемый ASCII importer отклонит такой файл; утверждается отсутствие доказательства обещанного прямого импорта и наличие конкретных ошибок DATEV.

**Preview нового экспорта несовместим с UI.** `displayPreview` пропускает только первую строку и ожидает date;text;amount;currency. В DATEV после metadata идёт header полей, далее amount;S/H;currency: заголовок становится операцией, валюта — суммой. BMD имеет другое расположение полей. Использовать typed JSON для preview и отдельный download endpoint, не разбирать целевой accounting export обратно в UI.

### 4.3. Retention, ресурсы и deployment — P1 (A16–A18), P2 (A20/A22)

`EarlyAuthAndBudgetMiddleware` — BaseHTTPMiddleware с проверкой объявленного Content-Length. Он действительно улучшает ранний отказ без Bearer, но не ограничивает поток без этого header, per-file размер, число страниц, строки, CPU или memory worker. Конвертация синхронна внутри async route; proxy timeout не останавливает CPU parser. Значения timeout в Settings сами по себе ничего не ограничивают.

Dockerfile USER appuser — полезное исправление. Но предложенный compose существует как Markdown-пример, задаёт `SQLITE_DB_PATH`, которого нет в Settings. Приложение использует DATABASE_URL и по умолчанию пытается создавать БД в `/app/statement2muster.db`; при read_only filesystem пример не обеспечивает запись. Mount `/app/data` не выбирается автоматически. PostgreSQL и его driver из ADR не внедрены.

Nginx example включает client_body_buffer_size=128k, но не предотвращает файловую буферизацию request/response. По умолчанию request buffering включён; body может быть принят proxy целиком до backend auth. Следовательно, tmpfs только внутри API-контейнера не закрывает retention на host proxy. Нужны ограниченный RAM-only путь на всём ingress, контроль client_body_temp_path/proxy_temp_path, cache/log/APM, swap и core dumps. Официальная семантика: [Nginx proxy buffering](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_request_buffering).

`/healthz` делает SELECT 1 и возвращает константу `zero_retention: enforced`. Это не проверка writable DB, mount options или удаления финансовых данных. Гарантию «полностью и немедленно удалено из RAM» нельзя выводить из окончания Python request: существуют копии bytes/строк, multipart, response и библиотеки. Практическая гарантия должна формулироваться как отсутствие durable retention под проверенной конфигурацией и завершение изолированного worker; не как криптографическое стирание heap.

### 4.4. Privacy, AVV и доверие — P2 (A23–A29)

Гражданское имя в юридических страницах — исправление, но не подтверждение регистрации/адреса. В исходном контексте указана Вена, в HTML — Klosterneuburg. Нужны согласованные реквизиты по фактическому статусу предпринимателя; не следует придумывать Firmenbuch/UID, если они неприменимы.

AVV из двух разделов не заменяет договор с условиями предмета/срока, категорий данных/субъектов, документированных инструкций, конфиденциальности, безопасности, subprocessors, помощи в правах и инцидентах, удаления/возврата и аудита. Zero retention не отменяет роль processor во время обработки. Privacy отдельно должна раскрывать retention billing/identity metadata и локальной истории. Это проверка полноты относительно [GDPR, Art.13/28/32](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng); окончательные юридические формулировки и применимость потребительских условий требуют проверки по реальной модели сервиса.

Firefox `data_collection_permissions.required=[none]` надо сопоставить с фактической передачей выписок и auth данных: декларация «none» не обосновывается отсутствием долгого хранения. Использовать действующие определения [Mozilla browser_specific_settings](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings). Старый PDF.js входит в опубликованный affected range; [Mozilla advisory](https://github.com/mozilla/pdf.js/security/advisories/GHSA-wgrm-67xf-hhpq) указывает условия eval и исправление. Эксплуатация в конкретном MV3-контексте отдельно не доказана.

Pilot runbook называет профили «сертифицированными», обещает CAMT, all ISO currencies, ISO-27001 Frankfurt и безопасный импорт при BALANCED. В проверенном коде нет подтверждающего корпуса/инфраструктурных документов. До evidence эти слова необходимо заменить на точную поддерживаемую матрицу и ограничения.

## 6. Условия повторного GO

18 зелёных unit/integration tests и совпавшие ZIP hashes не являются достаточным основанием для бухгалтерского пилота. Следующая приёмка должна быть привязана к новому конкретному commit/build и одновременно доказать: платёж выдаёт правильное право, чужой email его не получает, API не обходится replay/fallback, данные не превращаются в молчаливо неверные проводки, целевые программы импортируют эталон, а фактический deployment соответствует retention и договорным обещаниям.

До этих доказательств текущий release evidence следует считать **заявлением исполнителя, опровергнутым независимыми локальными проверками в перечисленных частях**, а не финальным разрешением на запуск.
