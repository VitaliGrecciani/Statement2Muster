## 1. Закрытые доказательные цепочки

**OOM / HTTP / квота / SQLite.** Проба создаёт отдельного tenant, выполняет настоящий HTTP POST на локальный Uvicorn `/api/v1/convert` с Bearer JWT, читает леджер через новые DB-сессии. Результаты: oom_kill +1, HTTP 422, RELEASED без RESERVED; следующий HTTP POST того же tenant — 200, одна транзакция и COMMITTED; integrity_check=ok. Условия раздела 2 Решения 21 выполнены. JWT формируется тестом с серверным ключом: эта проверка не является приёмкой OTP-доставки, что и не требовалось здесь.

**Живой карантинный worker / reclaim.** Проба подавляет оба механизма kill, проверяет реальную PID через неподменённый os.kill(pid, 0), восстанавливает механизмы и вызывает reclaim. Супервизор сохраняет Process-объект, выполняет kill/join и проверку завершения перед возвратом слота. Доставленные результаты PID 162, живой процесс до reclaim, отсутствие PID после, освобождение слота и успешный следующий разбор удовлетворяют разделу 3 Решения 21. Термин «без каких-либо mocks» в отчёте следует заменить на «контролируемая инъекция отказа с независимыми OS-проверками»: подмена kill здесь намеренная и допустимая.

**Происхождение.** Все 31 значения repo_source_manifest.json независимо совпали с SHA-256 Git blobs указанного build commit после LF-нормализации. Контейнерная сверка и image ID приняты как поставленные данные, повторно из контейнера не считывались.

## 2. Новый блокирующий дефект V6 — P1 / C07 / A18

В `backend/app/parsers/registry.py`, внутри `BankParserRegistry.parse_file`, до определения формата находятся две безусловные ветви:

- имя `__c07_adversarial_oom_probe__.csv` запускает бесконечное выделение блоков по 40 MiB;
- имя `__c07_slow_living_probe__.csv` запускает бесконечный цикл ожидания.

Нет ограничения тестовой средой, отдельной административной авторизации или зависимости от изолированной тестовой инъекции. Имя файла задаёт клиент. Авторизованный пользователь, допущенный к конвертации, может вызвать эти ветви обычной загрузкой маленького файла. Подтверждённый V6 HTTP/OOM-прогон непосредственно демонстрирует достижимость первой ветви через API.

Ограничение размера входа не ограничивает такое выделение памяти. Cgroup ограничивает общий контейнер, но не превращает намеренное исчерпание его ресурсов в безопасное штатное поведение. Наблюдавшийся выбор worker в качестве OOM-жертвы не гарантирует сохранность API при иных конкурентных нагрузках. Освобождение квоты после ошибки также не следует считать защитой от повторения.

Итог: механизм Recovery улучшен, но текущий релиз содержит доступный клиенту способ намеренно вызвать ресурсный сбой. Такой образ не получает инфраструктурный FULL GO.

## 3. Адресное исправление и окончательная приёмка

1. Удалить обе filename-ветви из выпускаемого `registry.py`. Перенести fault injection в тестовую оснастку отдельного изолированного экземпляра; обычный клиентский ввод не должен управлять режимом разрушительного тестирования.
2. Собрать чистый release image и обновить привязку commit/image/манифестов. Не переносить разрешение старого образа на новый только по номеру версии.
3. На чистом образе отправить нормальный небольшой CSV под обоими прежними именами. Проверить обычный разбор/штатный исход формата, отсутствие новых OOM-событий и таймаута, успешный следующий запрос. Добавить регрессию, что специальное имя не выбирает тестовый режим.
4. Сохранить принятые результаты Recovery V6 с явным указанием тестовой инструментализации. Повторять весь исторический аудит не требуется, если изменения ограничены удалением триггеров; изменения самого lifecycle или транзакционной логики требуют соответствующих адресных регрессий.
