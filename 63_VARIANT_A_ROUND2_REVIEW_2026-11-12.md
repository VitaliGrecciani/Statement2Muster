## 2. Блокирующие замечания

### R63-1 — P1: вторая запись кэша вытесняет первую до commit_quota

Места: `backend/app/main.py:498–526`, `backend/app/core/cache.py:105–134,200+`.

`canonical_operation_cache.set()` возвращает true. Затем `_idempotent_result_cache.set()` через SharedMemoryBudget может вытеснить только что созданную canonical-запись и тоже вернуть true. Условие `op_cached and idem_cached` проверяет прошлые результаты двух вызовов, а не наличие связанной пары перед списанием.

Независимая ASGI-проба моделирует допустимую границу общего бюджета: canonical-запись занимает 1851 байт по штатной estimate_size, общий бюджет — 1852 байта. Пара с replay-ссылкой уже не помещается. Получено:

```json
{"convert_http":200,"operation_issued":true,"canonical_present":false,"export_http":410,"committed_delta":1}
```

Это fault injection с уменьшенным RAM-бюджетом, а не утверждение о таком размере бюджета на production. Дефект алгоритма admission воспроизведён без конкурентных запросов: пользователь получает успешную платную конвертацию, результат которой уже нельзя экспортировать.

**Условие закрытия:** admission пары как одной логической операции с учётом полного размера и защитой от взаимного вытеснения до завершения commit; при невозможности сохранить пару — согласованное удаление, release RESERVED и 413 с нулевым COMMITTED delta. Простого сохранения bool от первого set недостаточно. Проверить: каждая запись помещается отдельно, пара не помещается; давление существующих записей; отказ одной вставки; отсутствие осиротевших ссылок и оплаченных недоступных результатов на момент ответа.

### R63-2 — P1: факториальный поиск цепочки блокирует обработку запроса

Места: `backend/app/services/reconciliation_service.py:115–151,256`; вызов из `backend/app/main.py:412`. Аналогичный синхронный перебор: `extension/app.js:1672–1698`.

Ограничение `max_solutions=2` прекращает поиск после двух найденных решений, но не ограничивает работу при отсутствии решения. Проба использует 12 сегментов, то есть штатный MAX_FILES_PER_BATCH:

- 11 разных выписок с одной датой, каждая с остатками 0 → 0 и реальными двумя операциями +100/-100;
- одна отдельная выписка 1000 → 1100 с операцией +100;
- номера выписок отсутствуют; содержимое различается, поэтому это не дубли.

Все сегменты внутренне сбалансированы, но общей цепочки нет. После подтверждения входа в реальную `_chain_file_segments` процесс не завершился в пределах общего 6-секундного таймаута и был остановлен. Это изолированная проба функции, не нагрузочный HTTP-тест. Структура алгоритма объясняет результат: перебираются перестановки большой несвязной группы.

Сверка выполняется синхронно в async endpoint, уже после parser supervisor. Поэтому его process timeout/hard kill не защищает event loop от этого расчёта. В offline-клиенте тот же подход создаёт риск зависания UI.

**Условие закрытия:** алгоритм с ограниченной сложностью (например, проверка связности и мемоизация состояний) либо жёсткий бюджет поиска с явной блокирующей диагностикой при исчерпании. Не выбирать произвольную цепочку. Проверить верхнюю допустимую размерность, отсутствие решений и неоднозначность на backend и offline; добавить проверку отзывчивости API/UI. Один AbortController на клиенте не прекращает синхронную работу сервера.

## 3. Остальные условия до RELEASE_DECISION

### R63-3 — P2: 12-tx baseline не соответствует контрольным остаткам Решения 62

`backend/test_bmd_bankauszug_erste.py:1019–1075` создаёт **одну страницу**, opening=1000.00, две положительные операции 471.66 и 462.76, расходы 460.00, closing=1474.42. Assert проверяет сумму положительных операций 934.42.

В Решении 62 требовалось другое: **opening 471.66 + общий net turnover 462.76 = closing 934.42**, 12 операций для исходного merged-сценария. Превращение opening и net turnover в две операции не является проверкой этого baseline. Visa baseline на пять операций согласован и проходит.

**Закрытие:** отдельная синтетическая fixture для шести сегментов 029–034 с 12 операциями, требуемыми начальными/конечными остатками, комиссиями и проверкой суммы ВСЕХ операций. Сохранить полезные текущие вариации отдельно. Проверить такие же данные через pdf.js; не переносить реальные PII.

### R63-4 — P2: прямой CSV replay заново генерирует DATEV metadata

`backend/app/main.py:311–314` повторно вызывает render_export_bytes для COMMITTED CSV-запроса; `backend/app/exporters/datev.py:18–19` берёт текущее время. Два POST `format=datev` с одинаковым payload и X-Idempotency-Key, разделённые 1.1 секунды, дали 200/200, но разные SHA-256. В поле создания EXTF изменилось `20261112130046000` → `20261112130047000`.

Повторного парсинга или искажения сумм эта проба не показывает. Нарушается воспроизводимость именно ответа на повтор той же операции.

**Закрытие:** фиксировать export metadata на операции либо сохранять готовый ответ в согласованном RAM-бюджете. Повтор того же POST в пределах TTL должен возвращать те же байты без нового времени создания. Для нового формата можно формировать отдельный экспорт; timestamp и его контракт должны быть определены явно.

### Границы browser smoke и сборочного доказательства

`test_browser_smoke.py` действительно запускает Chromium и pdf.js для обеих папок расширений. Но обе проверяются через `p.chromium.launch`, с подменой chrome API и перехватом downloads; это не запуск установленного Firefox-расширения. API направляется через ASGI bridge, не публичный Nginx. Landing проверяет реальные браузерные download-файлы; parsing PDF в его тесте выполняет backend.

В browser smoke проверены DATEV и BMD Bankauszug; нет скачивания BMD NTCS 8-column. Покрыт convert timeout, но не отдельные GET export timeout и зависшее чтение тела после быстрых headers. До финального решения дополнить эти адресные проверки, сохранив нынешние полезные тесты. Нативные Chrome/Firefox-проверки пакетов вынести в release acceptance и не обозначать имеющийся Chromium-тест как уже выполненную нативную Firefox-приёмку.

Сборщик воспроизводит текущие overrides, но его собственный `--check` лишь печатает хэши manifest/background, не сравнивает их с вычисленными ожидаемыми байтами. Добавить такое сравнение в сам check; в этой ревизии оно отдельно выполнено и прошло.

## 4. Обязательные проверки после разрешённого деплоя

Этот перечень не разрешает текущий deploy. После исправлений и повторного разрешения на контролируемый выпуск:

1. Зафиксировать release commit, package hashes, image digest, container ID и совпадение исходников контейнера; проверить runtime TTL=600s, общий RAM-бюджет и лимиты. Проверенное сейчас dirty tree не равно будущему образу.
2. Через публичный HTTPS reverse proxy проверить no-store, private на CSV/JSON, включая 401/403/410/413/422, Content-Type/Content-Disposition, доступность нужных заголовков через CORS, отсутствие proxy caching финансовых результатов.
3. Конвертация с target_format: блокирующий разбор/невыбранная Valuta → preview 422 и 0 списаний; успех → одна оплаченная операция, переключение трёх форматов без повторного списания. Сверить реальные BOM/Windows-1252, CRLF, 22/8 колонки, суммы, Konto/Gegenkonto, reference и имя файла.
4. Чужой tenant → отказ; истёкший JWT → 401; replay не вызывает parser и не продлевает TTL. После TTL/restart/eviction → 410 без нового списания; тестировать частичное вытеснение и admission boundary на изолированном стенде.
5. Проверить header/body timeout и восстановление UI для convert/export, reset/новая загрузка во время ответа. Установленные Chrome и Firefox пакеты: настоящий download API, доступ к шлюзу, смена формата и Valuta.
6. Подтвердить ограниченность работы reconciliation на несвязном максимальном batch и отзывчивость health endpoint. Реальные финансовые документы для этой проверки не нужны.

Внешний импорт в реальную BMD NTCS и бизнес-решение PO о default Valuta остаются прежними отдельными условиями. Закрытые C07/Managed Auth/Stripe-блоки этим решением целиком не переоткрываются.
