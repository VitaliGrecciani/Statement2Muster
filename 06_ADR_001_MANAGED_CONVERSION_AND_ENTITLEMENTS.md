# ADR-001: Managed EU Conversion, Identity, Entitlements and Transaction Integrity

- **Статус**: Accepted
- **Дата**: 2026-09-08
- **Авторы**: Chief Architect (Codex), Systems Engineer (Antigravity), Product Owner (Vitali Grecciani)
- **Основание**: Аудиторский реестр от 08.09.2026 (A01–A31), дорожная карта R0–R6

---

## 1. Контекст и проблематика

Аудит кодовой базы Statement2Muster выявил расхождение между продуктовыми обещаниями и фактической реализацией:
1. **Отсутствие серверной границы авторизации и прав (A01–A03)**: расширение использовало фиктивный логин и открытый доступ к локальному бэкенду; отсутствовал серверный учет прав по оплаченным чекаутам Stripe.
2. **Риск финансовой порчи данных (A08–A13)**: наивная дедупликация стирала реальные операции; псевдо-фильтр разделения клиентов (Anti-Mix) смешивал операции компаний А и Б в обе выгрузки; суммы и знаки определялись эвристически.
3. **Нарушение Zero Retention (A16–A17)**: конфиденциальные данные (IBAN, фрагменты выписок, имена) писались в логи, а OCR сохранял промежуточные файлы на диск без гарантированного затирания.
4. **Несовместимость сред (A20–A21)**: Docker-образ для Linux содержал Windows-зависимости (`winsdk`), а расширение для Firefox падало из-за вызова Chrome SidePanel API.

Данный ADR фиксирует обязательный архитектурный контракт системы для перехода к этапам реализации **R2 (Биллинг и права)**, **R3 (Безопасность среды)** и **R4 (Финансовая корректность)**.

## 2. Архитектура целевой системы

Система строится по модели **модульного монолита с управляемым EU бэкендом**:

```mermaid
flowchart TD
  subgraph Client ["Недоверенный клиент (Extension / Web)"]
    UI[SidePanel UI / Preview]
    AuthC[Auth Flow: launchWebAuthFlow + PKCE]
    Store[chrome.storage.session: JWT 10 min]
  end

  subgraph Gateway ["EU Managed Gateway / API (FastAPI)"]
    MW[Auth & Rate Limit Middleware]
    Quota[Quota Engine: Atomic Reserve / Commit]
    StripeWH[POST /api/v1/billing/stripe/webhook]
  end

  subgraph DB ["PostgreSQL (Identity & Ledger)"]
    Tenants[Tenants & Memberships]
    Entitlements[Entitlements & Stripe Mappings]
    UsageLedger[Usage Reservations & Idempotency]
  end

  subgraph Sandbox ["Изолированный Worker (Linux Subprocess)"]
    Worker[Parser & OCR Worker (tmpfs, memory-only)]
  end

  Client -->|Bearer JWT| Gateway
  Gateway --> DB
  StripeWH --> DB
  Gateway -->|In-memory stream / tmpfs| Worker
  Worker -->|Каноническая модель JSON| Gateway
```

### Принципы топологии:
1. **Управляемый EU backend (Hetzner, Франкфурт/Нюрнберг)**: является единым источником правды для платной конвертации, проверки тарифов и ведения квот.
2. **Расширение — тонкий недоверенный клиент**: выполняет выбор файлов, предварительный просмотр (preview), передачу параметров и сохранение выгрузки в браузере.
3. **Запрет скрытого fallback**: при ошибках доступа (401 Unauthorized, 403 Forbidden, 429 Quota Exceeded) клиент **никогда не переключается** на локальный клиентский движок конвертации. Ошибка отображается пользователю явно.
4. **Статический лендинг**: сохраняется как витрина продукта и перенаправляет на веб-авторизацию / чекаут.

## 3. Границы доверия и модель безопасности

* Клиент (расширение браузера) полностью недоверен. Никакие клиентские флаги (`isLoggedIn`, `plan = 'PRO'`, `features`) сервером не принимаются.
* Клиентское хранилище `chrome.storage.local` используется исключительно для пользовательских настроек интерфейса.
* Секреты Stripe (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`) находятся **исключительно на сервере** и ни при каких обстоятельствах не поставляются в клиентский дистрибутив.

## 4. Аутентификация и доставка прав

Для взаимодействия расширения с API предписывается протокол **Authorization Code + PKCE**:

1. **Вход пользователя**:
   - Расширение инициирует поток через `chrome.identity.launchWebAuthFlow`.
   - Сервер аутентификации производит проверку email через верифицированный Magic Link / одноразовый код.
   - Сервер возвращает одноразовый authorization code на строго валидированный Redirect URI расширения.
2. **Выпуск токена**:
   - Расширение обменивает код на короткоживущий **Bearer JWT (срок жизни 10 минут)**.
   - JWT подписывается асимметричным ключом (RS256 / EdDSA).
   - Claims JWT: `iss`, `aud`, `sub` (User ID), `tenant_id`, `sid` (Session ID), `iat`, `exp`. Никаких финансовых или банковских метаданных в токене не содержится.
3. **Хранение в расширении**:
   - Токен сессии хранится строго в `chrome.storage.session` (доступен только доверенным скриптам расширения, очищается при перезапуске браузера).
   - На MVP **Refresh Token в расширении не сохраняется**. Продление доступа происходит через действующую серверную веб-сессию с `HttpOnly` / `Secure` cookie.
   - Выход из системы (Logout) отзывает `sid` на сервере и мгновенно очищает `storage.session`.

## 5. Биллинг и серверные права (Entitlements)

1. **Обработчик вебхуков Stripe (`POST /api/v1/billing/stripe/webhook`)**:
   - Валидация подписи по исходному телу запроса (`stripe.Webhook.construct_event(raw_body, sig, secret)`). Неверная подпись → 400 Bad Request.
   - Таблица `stripe_event_inbox` обеспечивает строгую идемпотентность по `event_id`. Повторные события возвращают 200 OK без повторной выдачи прав.
2. **Модель прав (Entitlements)**:
   - Права привязаны к `tenant_id` и ведутся в реляционной базе данных.
   - Полномочия разделяются по типам: `subscription` (Starter, Business PRO) и `one_time` (Lifetime License).
   - Успешный возврат на Success URL чекаута носит исключительно информационный характер. Права вступают в силу **только после фиксации серверного события вебхука**.
   - События отмены (`customer.subscription.deleted`) или возврата (`charge.refunded`) аннулируют только связанное право, не затрагивая независимые лицензии тенанта.

## 6. Учёт квот и Fair Use

### 6.1. Единица тарификации
**1 успешно обработанный файл = 1 единица квоты**, независимо от количества страниц и строк внутри файла. 
*Пакетная загрузка (batch) из 12 файлов расходует 12 единиц квоты.*

### 6.2. Квоты по тарифам
| Тариф | Коммерческая квота |
|---|---|
| **Free Trial** | 3 успешных файла суммарно на верифицированного пользователя (создание нового tenant не сбрасывает триал). |
| **Starter** | 20 успешных файлов на tenant за оплаченный расчетный период Stripe (без переноса остатка). |
| **Business PRO** | Безлимит файлов в рамках расчетного периода (действуют технические ограничения Fair Use). |
| **Lifetime** | Бессрочное право согласно условиям покупки без искусственного ежемесячного лимита. |

### 6.3. Жизненный цикл списания (Двухфазный коммит)
1. **Атомарное резервирование**: До запуска парсера сервер резервирует необходимое число единиц (`status = RESERVED`) в транзакции базы данных. При нехватке квоты запрос отклоняется (429) до старта дорогостоящей обработки.
2. **Фиксация (Commit)**: Файл считается успешным только после прохождения парсинга, валидации схемы и проверки контрольных балансов. Успешный файл переводится в `COMMITTED`.
3. **Освобождение (Release)**: В случае повреждения файла, системной ошибки или неподдерживаемого формата зарезервированная квота возвращается клиенту (`RELEASED`).
4. **Идемпотентность**: Запрос сопровождается `idempotency_key`. Повторный запрос с тем же ключом и тем же телом возвращает ранее вычисленный результат без повторного списания квоты. Повторный запрос с тем же ключом, но другим содержимым → 409 Conflict.

### 6.4. Технические лимиты Fair Use (для PRO и Lifetime)
- Максимальный размер файла: 10 MiB (не более 50 MiB на batch-запрос).
- Максимум файлов в пакете: 12 файлов.
- Максимум страниц в PDF: 100 страниц; максимум операций на файл: 10 000 строк.
- Конкурентность: 1 активное задание конвертации на tenant одновременно.

## 7. Каноническая модель транзакции (Canonical Transaction Model)

До старта этапа R4 утверждается промежуточная нормализованная структура данных. Запрещается прямая трансляция разнородных regex-строк сразу в CSV.

### Иерархия изоляции данных:
$$\text{Tenant (Организация/Kanzlei)} \longrightarrow \text{Client Entity (Клиент/Фирма)} \longrightarrow \text{Account (Банковский счёт)}$$

* `tenant_id` назначается строго из контекста авторизованного JWT.
* Никакая операция не может быть экспортирована или показана без подтверждения принадлежности к `client_entity_id` и `account_id`.
* Имя файла, текст назначения и эвристики не могут служить первичными ключами изоляции.

### Схема полей транзакции:
| Поле | Тип | Назначение |
|---|---|---|
| `transaction_id` | UUID string | Уникальный суррогатный идентификатор операции |
| `tenant_id` | UUID string | Владелец учетной записи |
| `client_entity_id` | string | Идентификатор клиента Kanzlei (обязателен для экспорта) |
| `account_id` | string | Нормализованный IBAN или маскированный ID счета |
| `source_file_id` | string | Хеш/идентификатор исходного файла |
| `booking_date` | ISO Date (`YYYY-MM-DD`) | Дата проводки (с обязательным контролем границы года) |
| `value_date` | ISO Date (`YYYY-MM-DD`) | Дата валютирования (опционально) |
| `signed_amount` | Decimal string (напр. `"-12.34"`) | Точная сумма проводки со знаком (запрещены float) |
| `currency` | ISO 4217 (`EUR`, `USD`) | Валюта операции (запрещена принудительная подмена на EUR) |
| `description` | string | Очищенный текст назначения платежа |
| `reference` | string | Номер транзакции, референс банка или Belegnummer |
| `validation_status` | enum (`valid`, `ambiguous`, `error`) | Статус проверки полноты и корректности |

### Контроль полноты (Reconciliation):
Выходной объект `StatementResult` содержит:
- `opening_balance`, `closing_balance`, `turnover_debit`, `turnover_credit` (при наличии в выписке).
- `parsed_count`, `unparsed_lines_count`.
- При расхождении балансов или наличии нераспознанных строк финальный бухгалтерский экспорт помечается предупреждением и требует подтверждения бухгалтера.

## 8. Изоляция исполнения и Zero Retention (R3)

1. **Linux-совместимый Worker**:
   - Полное удаление Windows-специфичных зависимостей (`winsdk`, Windows Media OCR).
   - Распознавание сканированных PDF переводится на Linux-совместимый движок (Tesseract / EasyOCR) в изолированном пуле процессов.
2. **Ограничение времени и памяти**:
   - Парсинг выносится из основного event loop FastAPI в изолированные worker-процессы с жестким timeout (30 сек на digital, 90 сек на OCR) и лимитом памяти 512 MiB на процесс.
3. **Zero Retention и эфемерность**:
   - Запрет записи тел документов на постоянный диск.
   - Временные файлы размещаются исключительно в bounded tmpfs (RAM-диск).
   - Запрет логирования текста выписок, имен клиентов, полных номеров карт и IBAN. В логах фиксируются только `request_id`, время исполнения, число строк и коды ошибок.

## 9. Протокол ошибок и прозрачности

- **401 Unauthorized**: отсутствует или истек Bearer токен. Клиент предлагает повторный вход.
- **403 Forbidden**: активная подписка или права отсутствуют. Клиент открывает окно выбора тарифа.
- **413 Content Too Large**: превышен лимит байт (50 MiB) или страниц (100 стр).
- **415 Unsupported Media Type**: передан файл неподдерживаемого формата.
- **422 Unprocessable Entity**: синтаксическая ошибка структуры документа или нераспознанный банковский шаблон.
- **429 Too Many Requests / Quota Exceeded**: исчерпана квота файлов текущего периода.

---

## 10. Отклонённые альтернативы

1. **Полностью локальный офлайн-продукт без сервера**:
   - *Причина отклонения*: В расширении браузера невозможно защитить коммерческие лимиты (клик по счётчику, очистка local storage или правка JS снимают любые клиентские ограничения). Kanzlei требуется централизованное управление лицензиями и единые обновляемые парсеры.
2. **Использование общих вшитых License Keys**:
   - *Причина отклонения*: Вшитые ключи мгновенно утекают через декомпиляцию расширения и не обеспечивают гранулярного отзыва прав при возвратах платежей или отмене подписок в Stripe.

## 11. Критерии приёмки и переход к этапам R2–R4

Переход к реализации признаётся открытым при соблюдении условий:
1. **Утверждение ADR**: Статус документа переводится из `Proposed` в `Accepted` (Vitali Grecciani).
2. **Ветвление задач**:
   - Поток **R2**: Бэкенд авторизации, база данных PostgreSQL, Stripe Webhook, выдача/отзыв Entitlements.
   - Поток **R3**: Dockerfile на чистом Linux, удаление `winsdk`, настройка isolated worker и tmpfs.
   - Поток **R4**: Внедрение канонической модели транзакции, строгий парсинг дат/сумм (Decimal), DATEV/BMD валидация.
3. **Релизный гейт**: Публичный доступ к конвертации открывается только после одновременного завершения R2 и R3.
