## 1. Принятые результаты

- OOM-проба действительно выделяет память в дочернем процессе реального супервизора. Поставленный результат фиксирует рост `oom_kill` 1 → 2, PID/handshake 217, ошибку с exit code -9, завершение процесса, освобождение слота и успешный следующий разбор тем же супервизором. Этот компонент сценария 3.1 решения 20 принимается.
- Kill-failure-проба действительно активирует ошибочную ветвь: HTTPException 500, `last_job_reaped=false`, карантин и удержание одного слота. После снятия инъекции проба подтверждает восстановление слота и следующий разбор. Это подтверждает обработку **неподтверждённого** завершения.
- Fallback сравнения контейнера с самим собой удалён; отсутствие внешнего манифеста приводит к ошибке.
- Независимое чтение Git blobs `4268c7a9b3c8cef77fa92cdc154c52af17a190c1` подтвердило все 31 значения внешнего repo-манифеста после нормализации CRLF → LF. Предоставленная контейнерная сверка сообщает 0 нормализованных расхождений. Заявленный image: `sha256:7df1d46ca7ba19992831dda724950943a13e1fc27a406c2b149499fef9773c62`. Повторного чтения image на сервере не было.
- Ранее принятые Canary, CPU, Cancellation, перегрузка и персистентное размещение состояния сохраняют свой статус.

## 2. OOM: квота и состояние не входят в новую пробу

В `oom_script` создаётся отдельный `ParserProcessSupervisor`, вызывается `sup.parse_file(...)`, затем выполняется ещё один прямой вызов. В этом блоке нет HTTP-запроса `/api/v1/convert`, создания `UsageReservation`, чтения её итогового состояния или проверки SQLite после OOM.

Поэтому `subsequent_recovery_success=true` означает успешный вызов Python-супервизора, а не HTTP 200. Утверждения «резервирование квоты отменено» и «полная целостность SQLite после OOM подтверждена» не следуют из этой пробы. Ранее выполненный restart-тест не заменяет наблюдение этой цепочки.

В коде маршрута есть ветви `release_quota`; их наличие не равно эксплуатационной проверке результата транзакции. В частности, release выполняет flush, а dependency при исключении делает rollback. Это не объявляется доказанным дефектом: новая резервация также может корректно откатиться. Требуется проверить итог доступной квоты в отдельной DB-сессии.

**Адресная приёмка:** на тестовом экземпляре провести OOM через реальный convert-путь с резервированием; сохранить HTTP-исход, состояние квоты до/после из отдельной сессии, отсутствие зависшего RESERVED и успешный следующий HTTP-запрос того же tenant. Подтвердить доступность/сохранность состояния после события. Это оставшаяся часть сценария 3.1 решения 20, а не новое требование.

## 3. Kill/Reap: восстановление живого процесса пока не испытано

Проба подменяет `_pid_exists` и `_hard_kill_pid`, но **не подменяет `multiprocessing.Process.kill()`**. Производственный timeout-путь сначала вызывает `proc.kill()` и `proc.join(...)`. Следовательно, реальный worker может быть уже уничтожен и собран, пока `_pid_exists` искусственно продолжает сообщать True.

После снятия подмены `reclaim_quarantined_worker` может просто освободить слот уже мёртвого процесса. Это полезная проверка ложного сигнала о живой PID, но не доказательство заявленного восстановления реально оставшегося worker. В результате отсутствует измерение реальной живой PID непосредственно перед reclaim.

Реализация reclaim хранит только PID в set; она вызывает kill, sleep(0.05), затем `_pid_exists`. Она не хранит объект Process и не выполняет join/waitpid при reclaim. Поэтому жизненный цикл реально пережившего первоначальную очистку процесса требует отдельной проверки; текущая проба его обходит. Гарантия reaping живого карантинного worker из этих результатов не следует.

**Адресная приёмка:** в изолированной пробе подавить оба пути завершения только для целевого worker, дождаться карантина и независимым неподменённым средством подтвердить, что он действительно жив. Затем восстановить механизмы завершения, вызвать reclaim и подтвердить смерть, reaping без zombie, освобождение ровно одного слота и успешный следующий запрос. Реализация должна удерживать достаточные данные для подтверждённого join/reaping. Предусмотреть аварийную очистку самой пробы. Это завершение сценария 3.2 решения 20.
