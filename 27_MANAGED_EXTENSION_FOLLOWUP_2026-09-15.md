## 2. P1: истёкшая запись RAM-кэша обходит реестр

В is_token_revoked при `exp <= now` выполняется удаление записи и немедленный `return False`. При этом SQLite fallback для найденного отзыва заполняет кэш сроком `now + 600`, а не сроком действия JWT. Следовательно, у ещё действующего JWT после истечения этих десяти минут первый запрос может получить «не отозван», хотя запись в БД сохранена.

Локальная проба: время=1000, запись кэша=999, sqlite3.connect должен выбрасывать OperationalError. Результат функции: False; число обращений к connect: 0. При пустом кэше та же инъекция даёт 503. Это проверка функции; успешный полный HTTP-запрос здесь не воспроизводился. decode_access_token после False продолжает криптографическую проверку JWT, поэтому для неистёкшего токена эта ветвь не обеспечивает отзыв.

**Исправить:** после удаления истёкшей записи продолжать проверку реестра. Регрессия с JWT, чей exp ещё впереди: кэш TTL истёк, БД содержит отзыв → 401; тот же путь при ошибке БД → 503. Не смешивать срок жизни кэша со сроком действительности токена.

## 3. Доказательства остаются уже заявленного объёма

- Экспорт: раннер читает `currentCsvText` и `currentCsvFilename` через page.evaluate. Проверяет EXTF-префикс и >=12 строк; число проводок в отчёт записывается как 10. Нет реального download и проверки байтов Windows-1252, дат и сумм против исходника. Нужно получить файл через кнопку скачивания и проверить его содержимое.
- OTP всё ещё извлекается функцией get_db_otp_code из Hetzner DB. Для ранее запрошенной связанной цепочки нужен один UI-вход с кодом из письма, без сохранения секрета.
- Network/Timeout моделируется route.abort. Это доказательство немедленного сетевого отказа, но не истечения deadline при зависшем запросе. Добавить отдельный задержанный ответ и проверку восстановления UI.
- «Второй worker» в chain2 по-прежнему означает очистку кэша того же процесса. Нужна реальная отдельная инстанция/процесс для соответствующего утверждения. Некорректный CSV с 422 не эквивалентен аварии parser-worker.
- Повторный UI-вход после logout/restart следует явно подтвердить; отсутствие токена после рестарта само по себе не подтверждает повторный вход.

Это недостающие части прежних критериев, не новое расширение задачи.
