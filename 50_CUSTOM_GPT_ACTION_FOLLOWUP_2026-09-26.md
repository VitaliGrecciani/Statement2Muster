## 2. Принятые исправления

Принимаются следующие конкретные результаты:

- Удалены выдача PRO по demo-ключам, доверие Stripe-префиксам и поиск платных прав по неподтверждённому email. Пробы этих значений получают только анонимный режим, без платного плана. `check-license` исключён из маршрутов и схемы.
- Для JWT из заголовка сохранены корректные ответы: отозванный токен — 401, недоступный реестр — 503. Платные права читаются по проверенному tenant из активных, неистёкших entitlements.
- Подключён основной квотный сервис. Новый запрос Starter с уже израсходованными 20 единицами действительно отклоняется; фактический код — **429**, а не заявленный в отчёте 402.
- Анонимная квота теперь резервируется атомарно. При одной оставшейся попытке два конкурентных запроса дают один success и один `limit_reached`; итоговый расход равен 3. Это мягкий лимит клиентской сессии, а не устойчивый лимит подтверждённого пользователя.
- Middleware охватывает оба GPT-префикса. Пробы Content-Length и тела без Content-Length дают 413 при превышении бюджета. В коде ранний бюджет — `MAX_BATCH_SIZE_BYTES`, а файловый бюджет отдельно проверяется в adapter; это отличается от описания отчёта.
- Добавлены лимиты количества строк, raw UTF-8 input и base64 до/после декодирования. Невалидная дата, разные годы и разные валюты в проверенных structured-пакетах дают 422.
- YAML и JSON совпадают. Описание операции составляет **167 символов**, что укладывается в предел 300. Отказ от inline base64 для крупных файлов работает: пакет на 1500 строк вернул JSON размером 2067 символов без inline-файла.

Таким образом, изменения существенны, но утверждение «G01–G06 закрыты на 100%» не принимается.

## 3. Остаточные условия приёмки

### F01 / G01 — P1: нельзя превращать отказ проверки предъявленного JWT в анонимный success

В `resolve_verified_tenant` (`gpt_action.py:299–306`) общий `except Exception` поглощает исключения `decode_access_token`, включая HTTP 401 и 503. Для JWT в `license_key` выполняется переход в анонимную конвертацию.

Независимая парная проба:

| Состояние одного и того же токена / реестра | Authorization Bearer | JWT в `license_key` |
|---|---|---|
| Токен отозван | 401 | 200, success, plan=null |
| Реестр отзыва недоступен | 503 | 200, success, plan=null |

Это не выдача платного плана, но это обход заявленного fail-closed поведения нового пути. Возможность сознательно отправить отдельный анонимный запрос не оправдывает молчаливую подмену режима запроса с предъявленными учётными данными.

**Закрытие:** сохранить 401/503 для предъявленного JWT независимо от канала передачи. Отсутствие учётных данных и неуспешная проверка предъявленных учётных данных должны быть разными состояниями. Добавить парные header/body-тесты для отзыва, невалидной подписи и недоступного реестра. Не менять уже принятую базовую логику revocation ради этого adapter.

### F02 / G02 — P1: `session_id` не является идентификатором одной конвертации

Adapter использует `req.session_id` как `idempotency_key` всей беседы (`gpt_action.py:410–422`) и не передаёт `request_hash`. Основной квотный сервис возвращает существующую резервацию; adapter затем заново экспортирует другой payload.

Проба трёх разных выписок одной Starter-сессии дала три success с различными результатами (-10, -20, -30), но только **одну COMMITTED-резервацию на 1 единицу**, `request_hash=null`. Следующая невалидная выписка той же сессии получила 422 и через `release_quota` перевела уже оплаченную успешную резервацию в **RELEASED** (`gpt_action.py:597–603`).

**Закрытие:** отделить conversation/session ID от идентификатора операции. Связать идемпотентность с tenant, отдельным request ID и хэшем содержимого вместе с влияющими на результат параметрами. Разное содержимое под одним request ID должно получать конфликт либо отдельную операцию по явно выбранному контракту; настоящий повтор не должен повторно списывать квоту. Не разрешать ошибке новой попытки освобождать ранее COMMITTED-операцию. Для завершённого повтора определить возврат сохранённого результата и поведение после истечения RAM-кэша.

Адресные регрессии: разные выписки в одной беседе учитываются раздельно; 21-я отклоняется; идентичный повтор списывается один раз; изменённый повтор не использует чужую резервацию; ошибка после успешной операции сохраняет её COMMITTED-статус. Отдельно привести сведения о расходе Starter в ответе к действительному состоянию: текущие `conversions_used=0` и `remaining_free_conversions=9999` не являются его остатком квоты.

### F03 / G04–G06 — P1: исключение base64 не ограничивает весь JSON

У `default_bank_account` отсутствует достаточная валидация длины и формата. Проба с этим полем длиной 40 000 символов и тремя короткими проводками:

- Входящий JSON: **40 300 символов**.
- Ответ: HTTP 200, **162 031 символ**, inline base64 отсутствует.

Длинный счёт размножается в CSV preview и сопутствующих данных. Следовательно, обещание всегда укладываться в 5–8 KB либо в лимит Actions неверно. OpenAI требует вход и ответ менее 100 000 символов каждый. [Официальные ограничения GPT Actions](https://developers.openai.com/api/docs/actions/production).

**Закрытие:** установить согласованные server/schema-бюджеты для аккаунтов и остальных пользовательских строк, влияющих на экспорт, preview, URL/filename и сообщение. Некорректный бухгалтерский счёт следует отклонять, а не незаметно обрезать. Проверять размер всего сериализованного ответа, включая preview, notes и ошибки, с запасом относительно лимита Actions; ограничение одного `file_base64` недостаточно. Добавить приведённый контрпример и граничные тесты. Фактическое обрезание description/reference сейчас составляет 500/100 символов, а не 300/50 из отчёта; контракт и отчёт должны описывать выбранные пределы одинаково.

### F04 / G05 — неоднозначные даты всё ещё принимаются

Удаление fallback на `today()` принимается. Однако `parse_strict_date` пробует одновременно `%d/%m/%Y` и `%m/%d/%Y`. Строка `03/04/2026` получила success и была преобразована в `2026-04-03` по порядку форматов. Условие Решения 49 об отсутствии неявного выбора неоднозначной даты остаётся открытым.

**Закрытие:** для structured Action использовать объявленные однозначные форматы (например, YYYY-MM-DD и DD.MM.YYYY) либо явное поле формата/локали. Неоднозначный ввод без такого указания отклонять с 422. Проверить обе возможные интерпретации и отсутствие изменения даты без согласованного контракта.

### F05 / G03 — privacy-раскрытие нового канала ещё не завершено

Универсальные обещания сертификации/GDPR убраны; разделение backend/ChatGPT обозначено. Но API notes (`gpt_action.py:677`) и инструкции (`GPT_INSTRUCTIONS.md:94`) всё ещё обещают `unwiderruflich gelöscht` после 30 минут. В Решении 49 требовалось описать освобождение доступного RAM-результата, не гарантировать физическое безвозвратное стирание. Утрата ссылки не удаляет копии результата в разговоре ChatGPT.

**Закрытие перед реальными данными/публикацией:** убрать остаточное обещание, согласовать отдельный GPT-поток и TTL 1800 секунд в применимых публичных privacy/AVV-документах и досье, определить основания выбранного OpenAI-продукта/аккаунта. Прежний Stage 2 GO для старого маршрута не распространяется автоматически на новый. Это не препятствует отдельным синтетическим испытаниям.

## 4. Staging/Deploy Clearance и последующий G07

**На запрос обновить действующий `s2m-backend-api` ответ — NO-GO до закрытия F01–F04 и подтверждающей регрессии.** Разрешение на синтетическую разработку не является разрешением заменить production.

Разрешён отдельный staging на Hetzner с собственной тестовой БД и тестовыми учётными данными, ограниченным доступом, без production-томов и без реальных клиентских выписок. Для проверки Builder доступ организуется как контролируемый тестовый endpoint; весь API не становится общедоступным только ради теста. Это промежуточная проверка, не окончательное закрытие G07.

После исправлений зафиксировать для принимаемой сборки полные release commit, image ID, container ID, исходный манифест, health и OpenAPI. Затем проверить настоящий Custom GPT на синтетических данных: выбранный способ передачи подтверждённой личности, Starter-квоту, отказ авторизации, таймаут/повтор, крупный ответ и фактическое скачивание байтов Windows-1252 с контрольными суммами. Link-only delivery допустимо проверять как ссылку на скачивание; не объявлять его нативным файловым ответом Actions без соответствующего протокола и E2E. [Официальный протокол возврата файлов](https://developers.openai.com/api/docs/actions/sending-files).

Подготовить тестовые фикстуры так, чтобы новая временная БД корректно инициализировалась без зависимости от порядка тестовых модулей. 46/46 принимаются как регрессия подготовленного стенда, но не заменяют перечисленные отрицательные пробы.

Рабочий приоритет: **F01 и F02 → F03 и F04 → повторная адресная приёмка → G07**. F05 завершается до публикационного допуска и любых реальных данных через GPT.

C07, Managed Extension, Synthetic GO, S05 и ранее согласованный Stage 2 сохраняют принятые статусы в своих границах. Stage 1 DATEV/BMD остаётся открытым до внешнего бухгалтерского sign-off. Данное решение не требует повторно открывать эти блоки.
